# 自动追加保证金设计

## 背景

当前系统使用 2x 杠杆逐仓模式，配置 `close_threshold_pct: 10` 时，期货价格上涨约 36% 即触发强制平仓。由于套利持仓本质是对冲的（现货多头 + 期货空头），期货端浮亏对应现货端浮盈，仓位整体风险可控。被动强平会导致：

1. 丧失继续收取资金费的机会
2. 在基差尚未收敛时被迫平仓，可能造成实际亏损
3. 平仓后行情回落，错失了原本可盈利的头寸

**核心思路**: 在距爆仓距离缩小到预警区间时，自动向该仓位追加保证金以推远爆仓价，而非直接平仓。

---

## Gate API

**接口**: `POST /api/v4/futures/usdt/positions/{contract}/margin`

| 参数 | 类型 | 说明 |
|------|------|------|
| `settle` | path | 结算币种，固定 `usdt` |
| `contract` | path | 合约名称，如 `BTC_USDT` |
| `change` | query | 保证金变动量(USDT)，正数=追加，负数=减少 |

**效果**: 追加保证金后，逐仓仓位的爆仓价被推远（上移），`liq_distance_pct` 增大。

**前提**: 账户可用余额 >= change 金额。

---

## 风控层次重构

在现有三层风控基础上，新增"追加保证金"作为第 2.5 层（介于监控和紧急平仓之间）：

```
┌────────────────────────────────────────────────────────────────┐
│  第1层：预防性风控（开仓阶段）                                     │
│  - 距爆仓距离 < warning_pct → 禁止加仓                           │
├────────────────────────────────────────────────────────────────┤
│  第2层：监控性风控（持仓期间）                                     │
│  - 每5秒实时计算爆仓价和距爆仓距离                                 │
│  - 推送到前端持仓监控页面展示                                      │
├────────────────────────────────────────────────────────────────┤
│  第2.5层：【新增】自动追加保证金（主动防御）                         │
│  - 距爆仓距离 < margin_topup_pct → 尝试追加保证金                 │
│  - 追加成功后爆仓价被推远，距爆仓距离恢复                           │
│  - 追加失败或超限 → 降级到第3层紧急平仓                            │
├────────────────────────────────────────────────────────────────┤
│  第3层：应急性风控（平仓阶段，优先级0）                              │
│  - 距爆仓距离 < close_threshold_pct → 紧急平仓                    │
│  - 追加保证金已失败 或 追加次数超限 → 紧急平仓                      │
└────────────────────────────────────────────────────────────────┘
```

## 阈值设计

### 配置项

```yaml
# config.yaml 新增
margin:
  leverage: 2
  default_maintenance_rate: 0.005
  warning_pct: 15               # 禁止开仓
  topup_pct: 12                 # 【新增】触发自动追加保证金
  close_threshold_pct: 10       # 紧急平仓（追加失败的兜底）

  # 追加保证金策略
  topup:
    enabled: true               # 总开关
    target_distance_pct: 20     # 追加后目标距爆仓距离(%)
    max_topup_per_position: 3   # 单仓最大追加次数
    max_topup_ratio: 1.0        # 最大追加总额 / 初始保证金 比例（100%=最多翻倍保证金）
    min_gate_available: 50      # Gate 账户最低保留余额(USDT)，低于此值不追加
    cooldown_sec: 300           # 同一仓位两次追加间隔(秒)
```

### 阈值关系

```
 距爆仓距离
    ↑
   49%  ← 开仓时（2x空头，价格未变动）
    |
   20%  ← 追加后目标恢复到此位置 (target_distance_pct)
    |
   15%  ← 禁止开仓 (warning_pct)
    |
   12%  ← 触发追加保证金 (topup_pct) 【新增】
    |
   10%  ← 紧急平仓 (close_threshold_pct)
    |
    0%  ← 爆仓
```

## 追加金额计算

### 公式推导

目标：追加后 `liq_distance_pct` 恢复到 `target_distance_pct`。

逐仓空头爆仓价公式（追加保证金后）：
```
liq_price_new = future_open_price × (1 + (initial_margin + topup_total) / (qty × future_open_price) - maintenance_rate)
```

简化为（逐仓公式本质）：
```
liq_price = future_open_price + (initial_margin + topup_total) / qty - maintenance_rate × future_open_price
```

目标距离：
```
target_distance_pct = (liq_price_new - current_price) / current_price × 100
```

反推需要的 `liq_price_new`：
```
liq_price_new = current_price × (1 + target_distance_pct / 100)
```

需要追加的金额：
```
topup_amount = (liq_price_new - liq_price_current) × qty
```

### 实际计算示例

假设：
- 开仓价 = 100，当前价 = 130，qty = 1
- leverage = 2, maintenance_rate = 0.005
- 初始保证金 = 100/2 = 50 USDT
- 当前爆仓价 = 100 × 1.495 = 149.5
- 当前距爆仓 = (149.5 - 130) / 130 × 100 = **15%**（刚好 warning_pct）

当价格继续涨到 134：
- 距爆仓 = (149.5 - 134) / 134 × 100 = **11.6%** → 触发 topup（< 12%）
- 目标爆仓价 = 134 × 1.20 = 160.8
- 追加金额 = (160.8 - 149.5) × 1 = **11.3 USDT**
- 追加后保证金 = 50 + 11.3 = 61.3 USDT

## 决策流程

```
每轮平仓检查 (每0.5秒)
    │
    ├── 计算 liq_distance_pct
    │
    ├── distance >= topup_pct(12%) ?
    │   └── 正常，不做任何动作
    │
    ├── distance < close_threshold_pct(10%) ?
    │   └── 直接紧急平仓（无论追加状态如何）
    │
    ├── topup_pct(12%) > distance >= close_threshold_pct(10%)
    │   │
    │   ├── topup.enabled == false ?
    │   │   └── 跳过追加，等距离继续缩小后由 close_threshold 兜底
    │   │
    │   ├── 已追加次数 >= max_topup_per_position(3) ?
    │   │   └── 追加次数超限，不再追加，等 close_threshold 兜底
    │   │
    │   ├── 已追加总额 / 初始保证金 >= max_topup_ratio(1.0) ?
    │   │   └── 金额超限，不再追加，等 close_threshold 兜底
    │   │
    │   ├── Gate 可用余额 < min_gate_available(50) ?
    │   │   └── 余额不足，无法追加，等 close_threshold 兜底
    │   │
    │   ├── 距上次追加 < cooldown_sec(300) ?
    │   │   └── 冷却期中，跳过
    │   │
    │   └── 条件满足 → 计算追加金额 → 调用 Gate API 追加
    │       ├── 成功 → 记录追加记录，更新爆仓价
    │       └── 失败 → 记录日志，下轮重试或等 close_threshold 兜底
    │
    └── 继续检查其他平仓条件...
```

## 数据模型

### 持仓记录扩展

`mi_trade_position` 表新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `margin_topup_count` | INT | 已追加次数 |
| `margin_topup_total` | DECIMAL(16,6) | 累计追加金额(USDT) |

### 追加记录表（可选，用于审计）

```sql
CREATE TABLE mi_margin_topup_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    base_asset VARCHAR(20) NOT NULL,
    position_id BIGINT NOT NULL,
    contract VARCHAR(30) NOT NULL,
    topup_amount DECIMAL(16,6) NOT NULL COMMENT '追加金额(USDT)',
    liq_distance_before DECIMAL(8,2) COMMENT '追加前距爆仓距离(%)',
    liq_distance_after DECIMAL(8,2) COMMENT '追加后距爆仓距离(%)',
    gate_available_before DECIMAL(16,4) COMMENT '追加前Gate可用余额',
    success TINYINT(1) NOT NULL DEFAULT 1,
    error_msg VARCHAR(200),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_position (position_id),
    INDEX idx_asset_time (base_asset, created_at)
);
```

| `position_pnl_calculator.py` | 无变更（已计算 liq_distance_pct） |
| `closing_executor.py` | 在 `_check_margin_liquidation` 前新增 `_check_margin_topup` 逻辑 |
| `real_executor.py` | 新增 `_topup_gate_margin(contract, amount)` 方法调用 Gate API |
| `capital_tracker.py` | Gate 余额计算考虑追加金额 |
| `config.yaml` | 新增 `margin.topup` 配置块 |

### closing_executor.py 逻辑变更

```
check_and_close() 循环中:
    1. 首先检查 topup 条件（distance < topup_pct 且 distance >= close_threshold_pct）
       → 满足则调用追加逻辑
       → 追加成功则跳过本轮平仓检查（已脱险）
    2. 然后正常检查 _check_margin_liquidation (distance < close_threshold_pct)
       → 这是最终兜底，无论是否尝试过追加
```

## 爆仓价重算

追加保证金后，系统需要重新计算爆仓价。两种方案：

### 方案 A：本地重算（推荐）

追加成功后，更新持仓记录的 `margin_topup_total`，在下一轮 `position_pnl_calculator` 中：

```python
# 修改爆仓价计算，将追加保证金纳入
total_margin = initial_margin + topup_total
liq_price = future_open_price * (1 + total_margin / (qty * future_open_price) - maintenance_rate)
```

等价简化：
```python
liq_price = future_open_price + total_margin / qty - maintenance_rate * future_open_price
```

### 方案 B：从 Gate API 读取

调用 `GET /api/v4/futures/usdt/positions` 获取实时 `liq_price`。但这引入 REST 依赖，不推荐放在高频路径。

**结论**: 采用方案 A，本地重算，与现有架构一致。

## 风险控制

### 防护机制

| 风险 | 防护措施 |
|------|---------|
| 价格持续暴涨，追加耗尽资金 | `max_topup_ratio` 限制单仓最大追加比例 |
| 多仓同时触发追加，资金争抢 | `min_gate_available` 保证最低账户余额 |
| 频繁追加（震荡行情） | `cooldown_sec` 冷却期防止反复操作 |
| 追加后价格继续恶化 | `close_threshold_pct` 作为最终兜底 |
| API 调用失败 | 失败不阻塞主循环，下轮重试 |
| 追加金额计算误差 | 采用保守目标距离，留有冗余 |

### 最坏情况分析

假设初始保证金 50 USDT，`max_topup_ratio: 1.0`：
- 最大追加总额 = 50 USDT
- 最大单仓投入保证金 = 100 USDT（相当于无杠杆）
- 最坏损失 = 100 USDT（但对应现货端浮盈约 100 USDT，套利整体仍接近保本）

---

## 与现有体系的兼容性

1. **不改变 close_threshold_pct 的兜底语义**: 追加保证金是"优先尝试"，如果失败或超限，仍然由 close_threshold 触发平仓
2. **不影响其他平仓条件**: 止盈、资金费次数、累计负费等条件不受影响
3. **逐仓隔离不变**: 追加的保证金仅归属该仓位，不影响其他仓位
4. **capital_tracker 口径更新**: Gate 可用余额需减去累计追加金额
