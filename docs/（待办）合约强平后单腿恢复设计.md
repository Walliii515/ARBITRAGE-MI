# 合约强平后单腿恢复设计

> 状态：**草稿（未实现）**
> 关联文档：[开仓&平仓规则.md](./开仓&平仓规则.md)、[自动追加保证金设计.md](./自动追加保证金设计.md)、[风控规则.md](./风控规则.md)

---

## 背景

当前系统的保证金风控（详见 `开仓&平仓规则.md` 三层风控）建立在一个隐含假设上：

> **行情是渐进变化的，5 秒级监控 + 0.5 秒级平仓检查能在交易所强平之前主动平仓。**

但在以下极端场景下，该假设可能失效：

1. **瀑布行情/插针**：小市值标的瞬间拉涨 30%+，期货空头跨越爆仓价
2. **交易所故障/网络抖动**：监控数据延迟，本地未及时检测到 `liq_distance_pct < close_threshold_pct`
3. **多仓同时触发紧急平仓**：Gate 撮合延迟，部分订单被强平先于系统平仓单成交

一旦合约侧被交易所强制平仓，本地仍记录为 `holding`，系统会按"两端持仓"逻辑继续动作，导致：

- 平仓时 future 端报错（仓位不存在），整组失败 → 进入 60 秒冷却 → 现货裸露
- 或 spot 卖出成功、future 失败 → **单腿持仓**（仅剩现货多头敞口）

---

## 现状缺陷

| 维度 | 现状 | 风险 |
|------|------|------|
| 交易所持仓对账 | ❌ 无 | `mi_trade_position` 与 Gate 实际持仓可能脱节 |
| 平仓失败归因 | ❌ 整组成功/失败二态 | 无法识别"对手已不存在"vs"行情过差" |
| 单腿检测 | ❌ 无 | 现货敞口暴露时间不可控 |
| 单腿恢复 | ❌ 无 | 需运维手工处置 |
| 告警通道 | ❌ 仅日志 | 无主动通知 |

涉及核心文件：
- [src/calc/closing_executor.py](../src/calc/closing_executor.py)
- [src/calc/position_tracker.py](../src/calc/position_tracker.py)
- [src/calc/service_lifecycle.py](../src/calc/service_lifecycle.py)
- [src/calc/real_executor.py](../src/calc/real_executor.py)

## 设计目标

1. **检测**：能在 30 秒内发现"合约已被交易所强平、本地仍为 holding"的状态
2. **归因**：平仓失败时能区分"对手不存在"与"行情/深度问题"
3. **恢复**：识别单腿后自动平掉剩余腿，恢复到无敞口状态
4. **告警**：单腿状态写入告警表 + 醒目日志，运维可追溯

---

## 设计方案

### 方案 A：周期性持仓对账（推荐先做）

**入口**：在 `service_lifecycle.py` 注册一个低频任务（30 秒/次）

**流程**：
```
每 30 秒
  ├── 查 mi_trade_position 中 status='holding' 的全部记录
  ├── 调用 Gate API: GET /futures/usdt/positions
  │   （也可以走 WS 持仓订阅，避免 REST 频率限制）
  ├── 比对：本地有 holding 但 Gate 实际 size=0 的记录
  │   └── 标记为 force_liquidated_detected
  │       ├── 现货侧若仍有持仓 → 触发单腿平仓（仅 spot sell）
  │       ├── 现货侧也已不存在 → 直接结清记录
  │       └── 写入告警表 + 醒目日志
  └── 比对：Gate 有持仓但本地无记录（异常，先记录告警，不处理）
```

**新增配置**（`config.yaml`）：
```yaml
margin:
  reconcile:
    enabled: true
    interval_sec: 30          # 对账周期
    auto_close_orphan_spot: true  # 自动平掉单腿现货
```

**新增字段**（`mi_trade_position`）：
- `force_liquidated_at` DATETIME NULL — 检测到强平的时间
- `close_failure_reason` VARCHAR(64) NULL — 平仓失败归因

---

### 方案 B：平仓失败归因（推荐与 A 同步做）

**入口**：[closing_executor.py → _execute_close()](../src/calc/closing_executor.py)

**改造点**：当 `exec_result['success']=False` 时，根据 future 侧失败原因分流：

| 失败原因（Gate 错误码/message） | 归因 | 后续动作 |
|----------------------|------|---------|
| `POSITION_NOT_FOUND` / `INVALID_POSITION_SIZE` / size 不匹配 | `liquidated_by_exchange` | 立即标 force_liquidated，**继续尝试 spot 单腿平仓** |
| `INSUFFICIENT_AVAILABLE` / depth 不足 | `liquidity_issue` | 进入 60s 冷却，下轮重试 |
| 其他 | `unknown` | 进入冷却 + 告警 |

要点：**避免现状的"整组失败 = 全部回退"**，需要拆分两端的成交结果。

---

### 方案 C：单腿状态机（兜底）

无论检测路径如何，一旦标记为单腿，统一走单腿处置流：

```
holding(force_liquidated_detected)
    │
    ├── spot 仍有持仓 → 触发 spot 单边市价 sell
    │   ├── 成功 → status='closed'，close_reason='force_liquidated_by_exchange'
    │   └── 失败 → 进入 single_leg_alert 状态，告警，等下轮
    │
    └── spot 已无持仓（用户/外部已处理）→ status='closed'，无需动作
```

---

### 方案 D：根因消除——落实自动追加保证金

详见 [自动追加保证金设计.md](./自动追加保证金设计.md)（2.5 层风控）。
追加保证金能从**根上**推远爆仓价，降低瞬间击穿概率，是治本方案。
建议在 A/B/C 落地后再做 D。
