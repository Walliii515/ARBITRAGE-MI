# 基础对账功能设计

> 范围：Binance 现货 + Gate 期货持仓对账（本期不含资金/保证金/盈亏维度）
> 状态：设计稿，待实施
> 关联代码：`src/calc/position_tracker.py`、`src/calc/capital_tracker.py`、`src/calc/real_executor.py`、`src/calc/service_lifecycle.py`、`src/api/trading_api.py`

---

## 1. 背景与目标

### 1.1 现状
当前系统的持仓与资金状态由本地表 `mi_trade_position` 与内存计算共同维护：

- 持仓数量：开仓时由 `PositionTracker.create_position()` 写入 `spot_open_qty / future_open_qty / future_open_contracts`，平仓后状态置为 `closed`。
- 资金口径：由 `capital_tracker.calculate_account_summary()` 基于本地持仓 + 配置的 `binance_initial / gate_initial` 推算。
- 真实成交后，本地存的是经过手续费扣减的"净量"，与交易所账户余额理论上一致。

### 1.2 风险点
- 单边成交（如 `RealExecutor.execute()` 中 critical 日志场景）会造成本地与交易所不一致。
- 网络抖动、订单回执解析异常、人工干预（在交易所手动平仓/转账）均会引入漂移。
- 资金费、强平、ADL 等事件未在本地完整建模。

### 1.3 目标
建立"交易所为准 + 本地辅助"的混合数据源对账机制：

1. 定时拉取交易所真实持仓，与本地 `mi_trade_position` 聚合做差。
2. 差异落库 `mi_recon_snapshot`，供前端独立页面查询。
3. **本期仅记录差异，不告警、不自动修复**。
4. 表结构与代码骨架预留资金维度扩展位，下期一键开启。

## 2. 架构原则

- **混合数据源**：单交易所内的持仓/余额/盈亏以交易所 REST 为准；跨所聚合数据（总 PnL 等）仍由本地维护。
- **复用既有 HTTP 层**：在 `RealExecutor` 内追加只读拉取方法，复用现成的 Binance HMAC-SHA256 与 Gate HMAC-SHA512 签名逻辑（参见 `_binance_sign`、`_gate_sign`、`test_connectivity`），不重造请求层。
- **调度统一**：通过 `service_lifecycle.py` 注册定时任务，与 `funding_update` / `position_push` 等已有循环保持一致风格。
- **virtual 模式跳过**：本地账本模式下交易所无真实持仓，对账无意义。
- **只读不修复**：本期对账组件不会触发任何下单或修改本地表的逻辑。

```
┌────────────────────┐         ┌────────────────────┐
│ Binance REST       │         │ Gate REST          │
│ /api/v3/account    │         │ /futures/usdt/     │
└─────────┬──────────┘         │  positions         │
          │                    └──────────┬─────────┘
          ▼                               ▼
   ┌──────────────────────────────────────────────┐
   │ RealExecutor.fetch_*()  (新增只读方法)         │
   └────────────────────┬─────────────────────────┘
                        ▼
   ┌──────────────────────────────────────────────┐
   │ Reconciler.run_once()                         │
   │  · 本地聚合: SUM(spot_open_qty)/(future_      │
   │    open_contracts) GROUP BY base_asset        │
   │  · 与交易所数据 outer-join                    │
   │  · 差异计算 + 写入 mi_recon_snapshot          │
   └────────────────────┬─────────────────────────┘
                        ▼
        service_lifecycle 定时调度（默认 300s）
                        ▼
   ┌──────────────────────────────────────────────┐
   │ trading_api 暴露三个 REST 接口                │
   │ frontend /reconciliation 页面（AG Grid）       │
   └──────────────────────────────────────────────┘
```

## 3. 对账维度（本期）

| 维度 | 本地数据来源 | 交易所数据来源 | 比对单位 | 容差判定 |
| --- | --- | --- | --- | --- |
| Binance 现货持仓 | `mi_trade_position` 中 `status='holding'` 的 `spot_open_qty` 按 `base_asset` 求和 | `GET /api/v3/account` 返回的 `balances[].free + balances[].locked` | 币本位净量（已扣手续费） | `|exchange - local| <= 1e-6` |
| Gate 期货持仓 | `mi_trade_position` 中 `status='holding'` 的 `future_open_contracts` 按 `base_asset` 求和 | `GET /api/v4/futures/usdt/positions` 返回的 `size` 绝对值 | **张数**（避免 quanto_multiplier 浮点误差） | `|exchange - local| < 1` 张视为一致 |

### 3.1 比对单位选择说明
- **现货为何用币本位净量**：`RealExecutor._parse_binance_response()` 已将买入手续费扣除，本地存储即"净到账数量"，与交易所 `free + locked` 单位一致。
- **期货为何用张数而非币本位**：`future_open_qty = contracts × quanto_multiplier`，浮点放大可能导致一致的持仓出现 1e-12 级伪差异；张数为整数可精确比对。

### 3.2 不在本期范围
- USDT 可用余额、Gate 期货 margin、unrealised_pnl、funding_pnl 历史回放。
- 自动修复（如本地有持仓但交易所无 → 自动将本地标记为 closed）。
- 任何形式的告警（邮件、企业微信、`logger.critical`）。

## 4. 数据落库设计

### 4.1 新表：`mi_recon_snapshot`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK AUTO_INCREMENT | 主键 |
| `snapshot_at` | DATETIME NOT NULL | 本轮对账时间（同一轮所有记录共享同一值） |
| `exchange` | VARCHAR(16) NOT NULL | `binance` \| `gate` |
| `base_asset` | VARCHAR(32) NOT NULL | 标的资产，如 `BTC`、`XLM` |
| `dimension` | VARCHAR(16) NOT NULL | `position` \| `balance`(预留) \| `margin`(预留) \| `upnl`(预留) \| `error` |
| `local_value` | DECIMAL(30,10) | 本地聚合数值 |
| `exchange_value` | DECIMAL(30,10) | 交易所返回数值 |
| `diff_value` | DECIMAL(30,10) | `exchange_value - local_value` |
| `diff_ratio` | DECIMAL(20,10) | `diff_value / max(|local|,|exchange|,ε)`，供后续报表用 |
| `is_match` | TINYINT(1) | 是否在容差范围内一致 |
| `detail` | JSON | 原始字段（如 Gate `entry_price/unrealised_pnl/size`、Binance `free/locked` 拆分、错误堆栈摘要） |

索引建议：
- `INDEX idx_snapshot_at (snapshot_at)`：支持"最近一轮"查询。
- `INDEX idx_asset (base_asset, exchange)`：支持单资产历史趋势查询。

### 4.2 数据生命周期
- 写入：每次对账一轮 `N × 2` 条（每个资产 × 两个交易所）。
- 清理：定时任务循环末尾按 `retention_days`（默认 30 天）删除过期快照。
- 估算：100 个资产 × 2 交易所 × 每 5 分钟 1 轮 × 30 天 ≈ 173 万行，可接受。

## 5. 调度与配置

### 5.1 配置节（新增）
在 `src/config/config-live.yaml` 与 `src/config/config-virtual.yaml` 顶层追加：

```yaml
reconciliation:
  enabled: true            # 总开关
  interval_sec: 300        # 对账间隔（秒），默认 5 分钟
  retention_days: 30       # 历史快照保留天数
```

### 5.2 启动条件
- `trade.mode == 'virtual'`：**跳过**，不启动对账线程。
- `trade.mode in ('testnet', 'live')` 且 `reconciliation.enabled == true`：注册到 `service_lifecycle` 的循环线程列表。

### 5.3 失败兜底
单轮对账内部拉取异常（HTTP 失败、签名错误、解析异常）：
- 不抛出影响其他循环。
- 写入一行 `dimension='error'` 的快照，`detail` 含 `{exchange, error_msg, http_status}`。
- 下一轮按计划继续，不做指数退避（5 分钟间隔自然容错）。

## 7. 边界与扩展点

### 7.1 不做项（明确）
- 不实现资金、保证金、未实现盈亏维度对账。
- 不发送任何告警（包括 `logger.critical`、邮件、企业微信、前端弹窗）。
- 不修改本地 `mi_trade_position`，不触发任何交易动作。
- 不做跨所对账（如 Binance 现货数量 vs Gate 期货张数 × 乘数 一致性）——已由本地开仓逻辑保证，对账只验证"本地 vs 单一交易所"。

### 7.2 扩展点（下期可在不动表结构前提下加入）
| 维度 | 数据源 | 单位 | 容差建议 |
| --- | --- | --- | --- |
| `balance`（USDT 可用） | Binance `/api/v3/account` quote 资产；Gate `/futures/usdt/accounts` `available` | USDT | 相对差 1% |
| `margin`（Gate 逐仓保证金） | Gate position `margin` 字段 | USDT | 相对差 2% |
| `upnl`（未实现盈亏） | Gate position `unrealised_pnl` | USDT | 相对差 5%（盘口波动大） |

启用步骤：仅需在 `Reconciler.run_once()` 增加对应聚合逻辑与写入分支，并在前端 `dimension` 列展示即可，无需新建表。

## 附录 A：核心 SQL 草案

本地聚合（仅作伪 SQL，便于实施时参照）：

```sql
-- Binance 现货持仓聚合
SELECT base_asset, SUM(spot_open_qty) AS local_qty
FROM mi_trade_position
WHERE status = 'holding'
GROUP BY base_asset;

-- Gate 期货张数聚合
SELECT base_asset, SUM(future_open_contracts) AS local_contracts
FROM mi_trade_position
WHERE status = 'holding'
GROUP BY base_asset;
```
