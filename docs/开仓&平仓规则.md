# 交易逻辑说明

## 策略概述

跨交易所资金费率套利：**Binance 现货买入 + Gate 永续合约做空**，赚取正资金费率收入，并在基差收敛时止盈平仓。

订单簿监控中的“合约24h振幅”使用 Gate ticker 的 `(high_24h / low_24h - 1) × 100%`，随合约元数据每 5 分钟刷新。对本地仍为 `holding` 的标的，振幅达到 `50%` 且最新价位于 24h 高低区间顶部 `20%` 时写入铃铛；同一连续事件只提醒一次。振幅降到 `40%` 以下或最新价跌出区间顶部 `40%` 后视为恢复，后续再次达到触发条件才生成新提醒。该提醒只用于人工关注，不参与开仓或平仓决策。

- 保证金模式：Gate 正向永续固定为**全仓**，风险按账户级 MMR 和强平距离管理
- 决策频率：开仓循环 0.2s / 平仓循环 0.2s / 实时PnL与风控刷新 5s
- 模式开关：`trade.mode` ∈ {`virtual` / `testnet` / `live`}

### 标的分层

`mi_base_asset.strategy_tier` 用于区分标的质量：

| 分层 | 当前规则 | 策略含义 |
|------|----------|----------|
| A | Binance spot 24h 成交额 ≥ 1000万 USDT 且 Gate futures 24h 成交额 ≥ 500万 USDT | 主交易池，优先允许 momentum；未命中 momentum 时也必须走 pullback + resiliency + rebound |
| B | Binance spot 24h 成交额 ≥ 100万 USDT 且 Gate futures 24h 成交额 ≥ 50万 USDT | 可交易观察池，禁用 momentum，走 pullback + resiliency + rebound |
| C | 其他 | 谨慎池，默认不进入 WebSocket 订阅，不参与自动开仓 |

当前分层是“流动性分层”。后续积累 `signal_basis_bps / pre_gate_basis_bps / actual_basis_bps` 后，可以把 `execution_drift_p80 = pre_gate_basis_bps - actual_basis_bps` 加入分层：A 级要求 drift_p80 更小，C 级即使成交量达标也可因真实滑点差而降级。

### 行情画像

`mi_base_asset.market_profile` 与 `strategy_tier` 分开：`strategy_tier` 决定是否进入交易池，`market_profile` 决定开仓状态机如何处理盘口质量。

| 画像 | 含义 | 处理 |
|------|------|------|
| `normal` | 盘口更新较连续、双边流动性相对正常 | 使用普通 A/B 参数 |
| `thin_bursty` | 薄盘、跳动式更新，常见现象是长时间无增量后突然跳价 | 允许更宽的最终旁路新鲜度阈值，但缩小单笔金额，仍保留 entry_floor、盘口覆盖、resiliency、execution guard 和保护 IOC |
| `illiquid_blocked` | 低流动性/谨慎池 | 只观察，不应参与自动开仓 |

当前自动画像由 `update_asset_market_profiles` ETL 任务维护：A/B 标的中，如果 Binance spot 24h 成交额低于 `asset_market_profile.thin_spot_volume_24h_usdt`，或 Gate futures 24h 成交额低于 `asset_market_profile.thin_future_volume_24h_usdt`，标记为 `thin_bursty`；C 级标记为 `illiquid_blocked`。

`thin_bursty` 的原则是“监控更宽，执行更严”：系统不会因为 500ms 级别的稀疏更新立刻误杀所有机会，但真正下单前仍会重新读取单标的盘口，检查 lag/skew、entry_floor、覆盖率和执行保护。默认参数在 `trade.market_profile.thin_bursty`：

| 参数 | 默认 | 含义 |
|------|------|------|
| `open_amount_multiplier` | `0.8` | 单笔金额按普通金额的 80% 执行，避免 50% 小仓位触碰交易所最低开仓金额 |
| `max_orderbook_lag_ms` | `1500` | 最终旁路允许的单侧盘口最大滞后 |
| `max_book_skew_ms` | `1500` | Gate/Binance 最近更新时间最大偏差 |

WS 订阅由 `orderbook.strategy_tiers` 控制，当前默认 `[A, B]`。因此 C 级标的不会进入 Gate OBU 或 Binance depth20 订阅，也不会进入合并盘口、广播、VWAP 快照和开仓扫描热路径。

开仓通道由 tier 继续分流：`trade.momentum_open.allowed_tiers = [A]`，所以只有 A 级能走 momentum；`trade.rebound_open.allowed_tiers = [A, B]`，所以 A 级未命中 momentum 时、以及所有 B 级，都必须等待峰值回落、盘口恢复和回调后再突破。`trade.funding_carry_open.allowed_tiers = [A, B]` 是独立 carry 通道：当临近资金费结算且 24h funding 足够厚时，可不等待触顶回调，但仍必须通过盘口恢复、最终旁路和执行保护。

开仓入口不再只看 `open_basis >= p20`。系统会先计算一个统一的 `entry_floor`：它把 24h funding 的一部分、全程手续费、滑点缓冲和 p20 位置合并到同一套门槛里。后续 risk check、momentum、resiliency、rebound、pre-gate 和 execution guard 都使用这个 `entry_floor`，避免入口允许、后面又被旧 p20/盈利性守卫误杀。

极端正 funding 只限制新开仓，不触发已有仓位退出。实时 24h funding 达到 `300bps` 后，funding、Funding Carry、高基差等所有正向开仓通道统一拒绝；低于该值时，优质加仓继续按原有基差改善、集中度和交易所风险条件判断。实盘最终旁路取得 Gate REST 最新 funding 后会重新执行该检查和单币集中度检查，避免缓存值穿透上限。

## 1. 开仓流程

入口：[`TradingExecutor.check_and_open()`](file:///Users/jeffrey/Documents/MyProject/Arbitrage-Mi/src/calc/trading_executor.py)
触发频率：`trade.open.check_interval_sec = 0.2s`

### 1.1 全链路总览

```
每轮 0.2s 触发
    │
    ├─ 0. 数据完整性检查（盘口缺失 → 清状态跳过）
    ├─ 1. 风控检查（_pass_risk_check，下面 §1.2）
    ├─ 2. 冷却/降噪检查（开仓冷却 / 拒单冷却 / 回弹超时 / 信号噪音 / 执行漂移）
    ├─ 3. 开仓通道：标准 entry / funding carry 分流
    │   首次入场：实时校验 24h 资金费率（REST）；拿到实时值后覆盖本轮信号 funding 口径
    │   A. 动量通道（可选）：达到 entry_floor + buffer + 短窗口上升 + 盘口覆盖良好 → 直接进入最终旁路
    │   B. 回落通道：基差从峰值回落 ≥ pullback_pct + sustain 持续确认 → 进入盘口恢复确认
    │      A 未命中 momentum、以及 B 级标的：盘口恢复后不立刻下单，继续等待二次突破；
    │      若已明显高于 entry_floor 并稳定保持，则可走强安全垫确认
    │   C. Funding carry 通道：funding_24h≥30bps、basis≥max(开仓p20,平仓p20)-15bps、
    │      距资金费≤30min → 不等触顶回调，直接进入盘口恢复确认
    │   回落通道监控超时（基差长期不回落）：转为 timeout 直开候选，继续走盘口恢复与最终旁路
    │
    ├─ 4. 盘口恢复确认（orderbook resiliency，下面 §1.4）
    │   Gate future bid + Binance spot ask 深度恢复 / spread 未扩大 / basis 稳定 / 双边覆盖达标
    │
    ├─ 5. 最终风控旁路（_pre_execution_gate，下面 §1.5）
    │   单标的最短链路重新校验：盘口新鲜度 + 实时 funding 重算 entry_floor + 覆盖率
    │   执行保护：pre_gate 基差必须保留 entry_floor / 峰值衰减安全垫
    │
    └─ 6. 下单：调用 ExecutorClient → 持久化订单/持仓/信号，并记录 signal/pre_gate/actual 三段基差
```

### 1.2 风控检查（_pass_risk_check，全部通过才进入下一步）

| # | 检查项 | 配置项 | 默认值 |
|---|--------|--------|--------|
| 0 | Gate 全仓风险必须为新鲜的 `safe/idle`；`warning/danger/unknown` 均拒绝开仓 | `account_capital.gate_cross_risk.*` | 500%/300%，600/300bps |
| 1 | Binance/Gate 下单后可用资金均 ≥ 各自总资金比例 | `trade.open.min_*_available_ratio` | 15%/15% |
| 2 | 单标的 Binance spot 名义金额不超过 Binance 总资金比例 | `trade.open.max_asset_exposure_ratio` | 15% |
| 3 | `open_amount_usdt` ≥ 现货最小名义价值 | `trade.open.amount_usdt` | 10 USDT |
| 4 | 24h 资金费率(bps) ≥ 下限 | `trade.open.min_funding_rate_bps` | 15 bps |
| 5 | 开仓盘口覆盖率 ≤ 阈值 | `trade.open.orderbook_coverage_threshold` | 0.6 |
| 6 | 开仓基差 ≥ `entry_floor` | `trade.funding_adjusted_entry.*` + `mi_vwap_basis_threshold.open_basis_p20` | 见下 |
| 7 | 旧模式盈利性守卫：开仓基差 > 平仓基差阈值 + 全部手续费（仅 `funding_adjusted_entry.enabled=false`） | `trade.vwap.close_threshold_percentile` | `close_basis_p20` |
| 8 | 期货 24h 成交量 ≥ 阈值 | `trade.filter.min_future_volume_24h_usdt` | 15000 |
| 9 | 现货 24h 成交量 ≥ 阈值 | `trade.filter.min_spot_volume_24h_usdt` | 30000 |
| 10 | 交易所侧仓位风险不处于断腿状态 | `mi_trade_position.exchange_risk_status` | 非 `desynced` |
| 11 | 极端正 funding 不超过全局开仓上限 | `trade.open.positive_funding_guard.*` | 300 bps |

**统一入场门槛公式**：

```
expected_funding_bps = funding_24h_bps * funding_capture_ratio
carry_floor = min_expected_edge_bps + fee_full_bps + slippage_buffer_bps - expected_funding_bps
timing_floor = open_basis_p20 - min(max_funding_discount_bps, funding_24h_bps * discount_ratio)
entry_floor = max(carry_floor, timing_floor)

如果 funding_24h_bps < strong_funding_24h_bps:
    entry_floor = max(entry_floor, open_basis_p20)
```

含义：funding 很厚时，可以比 p20 略早一点进入，但最多只放宽 `max_funding_discount_bps`；funding 不厚时，不允许因为 p20 为负而低质量刷信号。

**Funding carry 独立通道**：

```
funding_24h_bps >= 30
current_basis_bps >= max(open_basis_p20, close_basis_p20) - 15
time_to_next_funding_min <= 30
strategy_tier in [A, B]
```

该通道不走“触顶回落 → 回调后再突破”，因为它抓的是临近结算前的 funding 收益窗口，而不是基差冲击释放后的二次上行。它仍复用 `_pass_risk_check` 的持仓数、保证金、资金、盘口覆盖、成交额过滤；触发后必须通过 orderbook resiliency、最终旁路实时 funding 复核、盘口新鲜度、覆盖率和执行保护。开仓原因会记录 `FundingCarry(...)`、距结算分钟数和本通道金额。

### 1.2.1 交易所侧断腿/ADL 风控

系统有两层交易所侧断腿防护：

第一层是 Gate 私有风险事件监听。实盘启动后订阅 Gate futures 私有频道：

```
futures.auto_deleverages
futures.liquidates
```

当 Gate 推送 ADL 自动减仓或强平事件时，系统会立即写入 `mi_exchange_risk_event`，按事件里的 `contract`、`trade_size/size`、`fill_price/order_price` 匹配本地 `holding` 仓位，把相关仓位标记为 `exchange_risk_status='desynced'`，然后自动卖出对应 Binance spot，补记 Gate 合约腿的交易所事件平仓记录，最后把本地持仓改为 `closed/resolved`。

第二层是定时 `Reconciler` 兜底审计，把本地 `mi_trade_position.status='holding'` 的聚合仓位与交易所真实仓位对账：

- Binance spot：对比本地现货持仓数量与 Binance 钱包余额，`BNB` 默认忽略，因为它用于手续费折扣。
- Gate futures：对比本地合约张数与 Gate 实际 futures position。

当 Gate 实仓小于本地 holding 仓位时，对账模块会回查最近 24 小时 Gate futures `my_trades`。如果成交记录中出现 `text=auto_deleveraging` 且 `close_size>0`，相关本地持仓会标记：

```
exchange_risk_status = 'desynced'
exchange_risk_type   = 'adl'
exchange_risk_at     = ADL 成交时间
exchange_risk_detail = ADL自动减仓|contract=...|close_size=...|pnl=...
```

如果没有识别到 ADL，但 Gate 实仓仍少于本地持仓，则标记为 `missing_gate_position` 或 `qty_mismatch`。如果 Gate 实仓大于本地正向持仓，则记录为 `extra_gate_position`。只要某个资产仍有 `exchange_risk_status='desynced'` 的 holding 仓位，开仓循环会跳过该资产，并把信号结束原因记为 `交易所仓位风险(desynced)暂停开仓`。

对账模块复用同一套兜底自动处置，并要求连续确认。默认 `confirm_runs=2`；首次异常落库后等待 `3s` 立即刷新本地、Gate 和 Binance 数据复核，不再等待下一次 `60s` 定时周期。只有 `15s` 内两次同方向异常都存在才允许实盘动作，避免单次交易所 API 抖动触发误操作：

- `missing_gate_position` / `qty_mismatch`：说明 Gate future 腿少于本地 holding，系统只做 reduce-only 风险收缩，自动卖出对应 Binance spot，并把本地持仓改为 `closed/resolved`。
- 当 Gate 已完全归零、全部 Binance 剩余现货都对应已确认的缺腿持仓，且总额低于 Binance 最低成交额时，兜底使用 Binance 官方小额资产转换将该币转为 BNB，再把相关本地持仓改为 `closed/resolved`。任一条件不满足都不会转换，避免处理同币种正常余额。
- Gate 已减仓而 Binance 仍有可交易裸多头时，对账按交易所净敞口聚合卖出，不按本地持仓笔数截断；成交数量分配回可解释该差异的 `desynced` 持仓。归零的持仓关闭并计算盈亏，重新平衡的持仓恢复为 `resolved`，仍有差异的继续保持 `desynced`。
- `extra_gate_position`：说明 Gate 多出正向策略的空头实仓，系统用 Gate `reduce_only` 买回多余合约；如果 Gate 多出的是 long position，则不按正向策略自动处理，避免误伤反向策略。
- 同一轮对账中，同一币种只能由一条已向交易所提交订单的自动处置路径持有执行权。Gate 差异仅被确认、缺少元数据/快照、余额不足但尚未下单，或只判定本地账本陈旧时，不得阻断后续基于两家交易所真实仓位的币种净敞口兜底；一旦任一路径已经调用交易所下单接口，无论成交、拒单或状态未知，其他路径都必须等待下一份新鲜快照，不能基于处置前快照重复下单。
- 自动处置数量只以同一轮 Binance 与 Gate 交易所实仓的净敞口为准。本地持仓账本与 Gate 实仓不一致、但交易所两腿仍平衡时只标记并等待账本修复，不得继续卖出现货；交易所确有裸多头或多余空头时也只减少真实差额。
- Gate 合约乘数缺失、为零或无法解析时，对账必须 fail-closed：保留异常快照并禁止该币的所有自动处置，不能默认按 `1` 换算。Gate 合约和 Binance 现货元数据的全量刷新都在单个数据库事务中完成，并在删除旧数据前校验关键字段及快照数量，读方只能看到刷新前或刷新后的完整数据。
- 服务缓存刷新遇到空快照、非法乘数/步长或相对上一版数量异常下降时保留最后正常版本。正反向新开仓在并发下两腿前必须通过 Gate 合约张数预检；已有仓位平仓优先携带持久化的 `future_open_contracts`，即使元数据暂时不可用也可按明确张数执行 reduce-only 减仓。
- 平仓执行器、ADL 处置和对账兜底共享按币种的减仓执行权；执行权从交易下单前保持到本地落库完成。其他线程遇到同币种正在减仓时直接跳过，等待下一份新鲜快照，不排队提交第二笔订单。
- 如果自动处置失败，风险事件写入 `mi_exchange_risk_event`，持仓继续保持 `desynced` 或风险未解除，开仓仍被阻断。

进入 `exchange_risk_status='desynced'` 的持仓不再进入普通平仓或 Gate MMR 风险平仓扫描，后续处置权统一交给对账兜底，避免同一 Gate 聚合仓位被重复减仓。

这条兜底路径的原则是 `reduce-only`：异常时只减少裸露风险，不自动补开缺失的一条腿。

### 1.3 开仓通道状态机

系统现在有三个开仓通道，但后续共用同一套盘口恢复、最终旁路、执行器、持久化逻辑。

#### 1.3.1 动量开仓通道（默认关闭）

动量通道用于你提到的“判断超阈值且处于上升期且盘口好的话直接开”。它不等待回调，也不走开仓 resiliency；它只负责把强势上升信号送到最终旁路，由旁路在下单前重新确认基差、盘口鲜度、覆盖率和盈利性。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.momentum_open.enabled` | true | 是否启用动量开仓通道 |
| `trade.momentum_open.allowed_tiers` | [A] | 允许走动量通道的分层；B 不在其中 |
| `trade.momentum_open.window_sec` | 1.2 | 默认短窗口；A 级由 `tier_overrides.A.window_sec=1.0` 覆盖 |
| `trade.momentum_open.min_samples` | 3 | 动量判断最少样本 |
| `trade.momentum_open.min_rise_bps` | 3 | 窗口内基差最小上升幅度 |
| `trade.momentum_open.min_basis_buffer_bps` | 8 | 默认当前基差需高于 p20 的额外安全垫；A 级覆盖为 6 |
| `trade.momentum_open.safety_bps` | 8 | 旧模式盈利性守卫额外安全垫；A 级覆盖为 6 |

状态机：
```
基差 ≥ entry_floor + buffer
短窗口样本数 ≥ min_samples
当前基差 - 窗口首个基差 ≥ min_rise_bps
当前基差接近窗口最高点（不是明显回落中）
覆盖率 ≤ coverage_threshold
实时费率校验通过
              → 创建 signal(trigger_type='momentum') → 最终风控旁路
```

#### 1.3.2 峰值回落 + sustain 开仓确认

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.peak_pullback.pullback_pct` | 0.05 | 从峰值回落 5% 触发开仓 |
| `trade.peak_pullback.sustain_sec` | 1.5 | 峰值监控最低持续秒数（过滤脉冲信号） |
| `trade.peak_pullback.monitor_timeout_sec` | 60 | 监控超时（基差长期不回落 → trigger='timeout'，进入盘口恢复与最终旁路） |

状态机（`_pass_peak_check`）：
```
基差首次 ≥ entry_floor → 实时校验24h费率(API) → 创建信号 + 记录峰值
基差更高        → 更新峰值
elapsed ≥ monitor_timeout_sec → 标记 trigger='timeout'，进入 RESILIENCY_WAIT（timeout）
基差 ≤ 峰值×(1-pullback_pct) 且 elapsed ≥ sustain_sec
              → 进入 RESILIENCY_WAIT（pullback）
RESILIENCY_WAIT → 后续每轮持续采样盘口恢复，不再反复要求 pullback 形态成立
恢复通过        → B 级进入 REBOUND_WAIT；其他未启用回弹确认的 tier 进入最终旁路
REBOUND_WAIT    → 基差从回调低点再次上行突破，或强安全垫稳定保持 → 最终风控旁路
回落但sustain不足 → 仅拦截本轮，状态保留到下轮重判
基差跌回 entry_floor 下 / 数据中断   → 清除状态
```

> **设计原则**：回落 + sustain 双重叠加，配合旁路 `lag_ms` 新鲜度硬约束。B 级新增 `rebound` 是为了避免“回调后第一口流动性继续衰减”：先确认盘口恢复，再等基差从回调低点重新上行，确认二次拉升后才开仓。

### 1.4 开仓盘口恢复确认（orderbook resiliency）

峰值回落通过后不立即下单，而是确认被冲击的开仓侧盘口已经恢复。该逻辑由 `calc/orderbook_resiliency.py` 统一实现，开仓侧观察：

- Binance spot ask 深度（现货买入会吃 ask）
- Gate future bid 深度（合约做空会吃 bid，按 `quanto_multiplier` 换算为 USDT）
- spot/future bid-ask spread 是否相对窗口起点扩大
- 最近窗口内 `open_vwap_basis_bps` 是否稳定
- `spot_open_coverage` 与 `future_open_coverage` 是否都在阈值内

状态机：
```
pullback confirmed
  → RESILIENCY_WAIT
  → 样本数不足 / 深度未恢复 / spread过宽 / basis波动过大 / coverage未恢复：继续等待
  → 等待超时：信号记为 gate_rejected，原因以 resiliency: 开头，放弃本轮
  → 条件连续满足 min_hold_sec：B 级进入回调后再突破等待，其他 tier 进入最终风控旁路
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.resiliency.enabled` | true | 是否启用开仓盘口恢复确认 |
| `trade.resiliency.window_sec` | 3.0 | 盘口恢复观察窗口 |
| `trade.resiliency.min_samples` | 2 | 窗口内最少样本 |
| `trade.resiliency.min_recovery_ratio` | 0.65 | 当前深度相对监控起点的最小恢复比例 |
| `trade.resiliency.max_spread_widen_bps` | 8 | spot/future spread 最大扩大幅度 |
| `trade.resiliency.max_basis_volatility_bps` | 6 | 窗口内开仓基差最大波动 |
| `trade.resiliency.min_hold_sec` | 0.4 | 恢复条件连续满足时长 |
| `trade.resiliency.max_wait_sec` | 5.0 | 等待恢复超时后放弃本轮信号 |

### 1.4.1 回调后再突破确认（rebound open）

A/B 级标的在 `pullback + resiliency` 通过后不会立刻开仓，而是进入 `REBOUND_WAIT`。A 级只有命中 momentum 时才能跳过这一步。`REBOUND_WAIT` 有两条通过路径：

**普通二次突破路径**：

```
resiliency passed
  → 记录回调低点 floor
  → 当前基差从 floor 至少回升 min_rise_bps
  → 当前样本相对上一样本仍向上 min_slope_bps
  → 当前基差 ≥ entry_floor + min_basis_buffer_bps
  → 最终风控旁路
```

**强安全垫路径**：

```
resiliency passed
  → 当前基差 ≥ entry_floor + strong_cushion_bps
  → 连续保持 strong_cushion_min_hold_sec
  → 最终风控旁路
```

强安全垫路径用于 SAHARA 这类情况：funding 和当前基差都很厚，但回调后基差横住，没有再额外拉升 4bps。它不绕过最终旁路和 execution guard，只是不再机械要求“从低点再涨 + 当前样本继续向上”。

成功触发强安全垫路径时，`mi_trade_signal.trigger_type` 记录为短码 `rebound_strong`。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.rebound_open.enabled` | true | 是否启用回调后再突破确认 |
| `trade.rebound_open.allowed_tiers` | [A, B] | A 未命中 momentum 时、以及 B 级，都使用回弹确认 |
| `trade.rebound_open.min_rise_bps` | 4 | 从回调低点至少回升多少 bps |
| `trade.rebound_open.min_slope_bps` | 0.5 | 当前样本相对上一样本仍需向上 |
| `trade.rebound_open.min_basis_buffer_bps` | 4 | 当前基差需高于 entry_floor 的额外安全垫 |
| `trade.rebound_open.max_wait_sec` | 5.0 | 盘口恢复后最多等待普通二次突破多久 |
| `trade.rebound_open.strong_cushion_bps` | 20 | 当前基差高于 entry_floor 多少 bps 后进入强安全垫确认 |
| `trade.rebound_open.strong_cushion_min_hold_sec` | 1.0 | 强安全垫连续保持多久才确认 |
| `trade.rebound_open.strong_cushion_max_wait_sec` | 8.0 | 强安全垫活跃时最多等待确认多久 |

等待期间如果基差跌回 `entry_floor` 以下，信号记为 `conditions_lost`；超过等待时间仍未二次突破、也未完成强安全垫保持，信号记为 `monitor_timeout`，并进入短冷却，防止同一段盘口状态反复刷信号。timeout 原因会记录 `floor/current/rise/slope/min_basis/entry_floor/strong_cushion/strong_hold/timeout`，用于判断到底是形态没起来，还是强安全垫保持时间不够。

### 1.4.2 执行质量保护（execution guard）

最终旁路通过后、下单前，还会检查 pre-gate 基差是否留有足够安全垫：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.execution_guard.enabled` | true | 是否启用下单前执行保护 |
| `trade.execution_guard.min_profit_buffer_bps` | 15 | 旧模式字段；新模式不再单独使用盈利性守卫 |
| `trade.execution_guard.min_p20_buffer_bps` | 3 | 新模式下表示 pre_gate 需高于 entry_floor 的额外安全垫 |
| `trade.execution_guard.max_peak_decay_bps` | 45 | pre_gate 相对峰值最多允许衰减多少 bps |

该保护不能替代真实 IOC/限价执行，但能先过滤“信号仍成立、实际已经太弱”的下单。

### 1.4.3 开仓基差审计字段

为了定位“触发时很好、成交时变差”的漂移，系统会同时记录三段基差：

| 字段 | 记录位置 | 口径 |
|------|----------|------|
| `signal_basis_bps` | `mi_trade_signal` / `mi_trade_order` / `mi_trade_position` / 开仓原因 | 触发时看到的开仓 VWAP 基差 |
| `pre_gate_basis_bps` | 同上 | 下单前最终旁路用最新盘口重算的基差 |
| `actual_basis_bps` | 同上 | 成交后按真实成交价计算的基差 |

成功开仓的原因里会追加：`基差对比(signal=...,pre_gate=...,actual=...)`，并同步写入 `mi_trade_signal.exit_reason`，所以交易信号页的“结束原因”列也能直接查看开仓复盘信息。

开仓原因里的 funding 口径以实时值为准：`carry(funding24h=...)`、`实时24h费率...`、订单表 `funding_rate_24h` 都使用最近一次 Gate 实时合约接口返回值。若实时值与缓存元数据不同，会额外记录 `缓存24h费率...(偏移...bps)`，方便判断是 Gate funding 快速变化，还是元数据刷新滞后。

### 1.5 最终风控旁路（_pre_execution_gate）

确认信号后、下单前的最后一道闸。**单标的最短链路**重读盘口、重算指标。

```
① 单标的盘口读取：gate_manager.get_orderbook(contract) + spot_manager.get_orderbook(symbol)
② 盘口新鲜度硬约束：now_ts − last_update_time ≤ max_orderbook_lag_ms（gate / spot 双侧各自判定）
③ 合并 + VWAP 基差重算
④ 基差 ≥ entry_floor？覆盖率达标？
   通过：用这份数据下单（数据=校验数据，零缝隙）+ 将 (gate_lag_ms, spot_lag_ms) 记入最近一次鲜度槽供原因拼接
   失败：信号标记 gate_rejected，清状态
   异常：退化为放行（不阻塞热路径）
```

> ② **鲜度闸** 是破除“旁路与 sustain 同源缺陷”的核心实践：以本地接收时刻（`last_update_time`）为准，反映“现在距上次收到 WS 增量多久”。交易所推送的 `update_time` 不可靠（快照重建后会“看起来很新”），本地接收时刻才是最接近客观事实的新鲜度判定。

该函数所有拦截分支均会输出详细日志（含时间戳、basis、lag等），通过分支也会打一行 `开仓旁路通过 | ...` 供复盘。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.open.max_orderbook_lag_ms` | 500 (ms) | 下单前本地盘口最大允许延迟；超过则拒绝本次开仓 |

### 1.6 冷却与降噪

| 触发场景 | 配置项 | 默认值 |
|---------|--------|--------|
| 同标的开仓后 | `trade.open.cooldown_sec` | 60 s |
| 峰值 60s 超时直开候选失败后 | `trade.peak_pullback.timeout_cooldown_sec` | 10 s |
| 被交易所拒单后 | `trade.open.reject_cooldown_sec` | 60 s |
| 回弹等待超时 | `trade.rebound_timeout_cooldown.cooldown_sec` | 60 s；基差变化 ≥ 5 bps 提前解除 |
| 单标的近 60 分钟信号过密但几乎不开仓 | `trade.asset_noise_cooldown.*` | 10 min |
| 成交后 `pre_gate_basis_bps - actual_basis_bps` 过大 | `trade.execution_drift_cooldown.*` | 30 min |

这些冷却只拦截新信号，不会中断已经进入状态机的信号。

## 2. 平仓流程

入口：危险路径使用 `ClosingExecutor.check_and_close_margin_danger()`；普通路径使用 `ClosingExecutor.check_and_close()`。
触发频率：`trade.close.check_interval_sec = 0.2s`

### 2.0 下架风险识别

下架风险由后台独立采集并写入内存风险报告，开仓和平仓热路径只读该报告。Gate 合约同时读取
`delisting_time`（进入只减仓）和 `delisted_time`（正式下架）；只要未来下架时间进入 30 天观察窗，
即使合约仍为 `trading`，也立即禁止该标的新开仓。已有仓位在距离正式下架不超过
`trade.close.delist_risk_exit_days`（默认 2 天）时进入下架风险退出。风险报告每 60 秒刷新一次。

### 2.1 平仓优先级（命中即触发）

| 优先级 | 触发条件 | 配置 | 是否走旁路 |
|-------|---------|------|----------|
| 0（最高） | **Gate 全仓危险**：MMR≤300% 或最近强平距离≤300bps | `account_capital.gate_cross_risk.*` | 否（紧急） |
| 1 | **负资金费风险**：当前24h负费率临近结算/极端恶化，或历史实际已付负资金费达到阈值 | `negative_funding_exit_*` | 是，风险旁路 |
| 2 | 资金费支付次数 ≥ 上限 | `trade.close.max_funding_payments`(30) | 是，风险旁路 |
| 3 | **动态净止盈**：收敛收益 + 已收资金费 - 全部手续费 ≥ 动态 bps；持仓老化后允许降低阈值上限 | `fixed_take_profit_bps` + `dynamic_take_profit` | 是，且先走盘口恢复 |

优先级 0 在服务循环中先于所有盘口服务、WS 和交易连通性判断执行。它只接受 `max_age_sec` 内的 Gate 统一风险快照；账户 MMR 危险时进入按风险贡献排序的分步恢复，单合约强平距离危险时只处理对应合约。`unknown`、`idle` 或陈旧快照只触发刷新，不会触发平仓。

账户 MMR `<=300%` 进入分步恢复模式，执行顺序与资金监控显示的首平候选一致：先处理距强平价 `<=300bps` 的合约并按距离由近到远排序，其余合约按维持保证金从高到低排序。每份新鲜账户风险快照最多成功平一笔，随后等待 Gate 刷新 MMR；低于 `500%` 继续下一笔，达到 `500%` 立即停止。每笔仍先执行 Gate `reduce-only` 市价买回，再处理 Binance 现货腿；失败后可尝试下一候选且不进入普通冷却。

**止盈公式**：
```
spread_profit_bps = open_spread_bps - current_spread_bps
funding_earned_bps = funding_pnl_bps    # 已收资金费 bps（含正负）
net_profit_bps = spread_profit_bps + funding_earned_bps - fee_full_bps
触发: net_profit_bps ≥ dynamic_take_profit_bps
```

当前默认 `fixed_take_profit_bps = 200`，动态止盈只负责在后续持有价值变弱时降低阈值，不会把阈值抬高到 200 以上。

**动态止盈阈值**：
```
funding_support_bps = 0.6 × 最近3次结算24h等效均值 + 0.4 × 历史p50
funding_potential_bps = min(历史p70, max(当前实时24h funding, funding_support_bps))

remaining_basis_potential_bps = max(0, current_close_basis_bps - close_basis_p20)
basis_score_bps = min(30, remaining_basis_potential_bps × basis_discount)

hold_value_bps = funding_potential_bps + basis_score_bps
```

`basis_discount`：A类 `0.45`，普通画像 `0.35`，`thin_bursty` `0.25`。如果同标的历史结算样本不足，系统降低置信度：3-5 个样本使用当前/最近均值/p50 的混合公式；少于 3 个样本时不激进降低止盈阈值。

动态阈值分层：

| hold_value_bps | 动态净止盈阈值 |
|---:|---:|
| ≥ 60 | 200 |
| ≥ 40 | 150 |
| ≥ 25 | 110 |
| ≥ 15 | 80 |
| ≥ 5 | 60 |
| < 5 | 45 |

**持仓老化止盈修正**：

动态止盈不是强制到期平仓；持仓时间只会降低止盈阈值上限，仍然要求净收益为正，并继续走谷底反弹、盘口恢复和最终旁路。

| 持仓时间 | 阈值修正 |
|---:|---:|
| < 5 天 | 使用正常动态阈值，最高 200bps |
| ≥ 5 天 | 动态阈值最多 100bps，且净收益至少 30bps |
| ≥ 8 天 | 动态阈值最多 60bps，且净收益至少 20bps |

原因中会记录 `aging(...)`，例如 `aging(aging,age=5.2d,raw=200.0,cap=100.0,min=30.0)`，用于复盘该平仓是否由持仓老化降低了阈值。

如果下一期预计正资金费足够厚，且距离结算在 `positive_funding_hold_window_min` 内，即使动态净止盈已达标，也会暂缓到结算后再重新评估。

**负资金费风险公式**：
```
current_negative_24h_bps = abs(funding_rate_24h × 10000)  # 仅当 funding_rate_24h < 0，用于判断当前环境恶化
paid_negative_bps = funding_rate_sum_bps                  # 历史实际已支付负单期资金费累计；正资金费不抵消
funding_net_bps = funding_pnl_bps                          # 已结算资金费净收益，收入为正、支出为负
time_to_next_funding_min = 距下一次资金费结算分钟数
进入监控:
  paid_negative_bps >= negative_funding_exit_paid_bps
  或 current_negative_24h_bps >= negative_funding_exit_extreme_24h_bps 连续确认2轮
  或 time_to_next_funding_min <= negative_funding_exit_watch_window_min
     且 next_funding_bps <= -negative_funding_exit_next_bps
  进入监控后暂停该币种继续开仓
择机退出:
  路径A（监控仓出现盈利点位）:
    当前24h资金费仍为负
    且 0 <= time_to_next_funding_min <= negative_funding_exit_opportunistic_window_min
    且 price_net_bps >= negative_funding_exit_opportunistic_min_net_profit_bps
  路径B（支付本次费用不如现在退出）:
    当前24h资金费仍为负
    且 0 <= time_to_next_funding_min <= negative_funding_exit_opportunistic_window_min
    且 next_funding_bps <= -negative_funding_exit_next_bps
    且 basis_loss_bps <= abs(next_funding_bps)
    且 basis_loss_bps <= negative_funding_exit_max_basis_loss_bps

price_net_bps =
  (open_basis_bps - latest_position_vwap_close_basis_bps)
  - estimated_full_round_trip_fee_bps

basis_loss_bps = max(
  0,
  latest_position_vwap_close_basis_bps - open_basis_bps
)
```

当前默认阈值：当前24h负费率连续两轮达到极端 `45bps`、历史实际已付负资金费累计达到 `7bps`，或距结算不超过 `30min` 且下一期预计不高于 `-7bps` 时进入监控，并暂停该币种继续开仓。监控仓在距下一次结算不超过 `60min` 时，可以按价格净空间 `20bps`（开平基差收敛减完整手续费）择机退出；也可以在下一期预计不高于 `-7bps` 时比较单次费用与基差损失，只有基差损失不大于本次预计负费且不超过 `60bps` 才退出。历史已付负费只用于进入监控和复盘，不参与当前执行价格判断。负 funding 不再拥有无视基差的强制退出权限；所有负 funding 退出都必须复核实际待平数量 VWAP、使用保护 IOC，并复用同币首笔成交质量保护。

> `take_profit_mode=legacy_p40` 时仍可回退到旧 p40 倍数止盈，但当前实盘配置使用固定净 bps。

### 2.2 谷底反弹确认（仅止盈使用）

| 配置项 | 默认值 |
|--------|--------|
| `trade.valley_rebound.rebound_pct` | 0.10 |
| `trade.valley_rebound.monitor_timeout_sec` | 60 |

谷底状态按 `position_id` 隔离；同一标的多笔持仓不会互相覆盖 valley / timeout / rebound 状态。

状态机：
```
止盈首次满足 → 记录 valley_bps + start_time
基差更低     → 更新 valley
基差 ≥ valley + (open_spread_bps - valley) × rebound_pct → 反弹确认平仓
elapsed ≥ timeout → 直接平仓（保底）
止盈不再满足 → 清除状态，放弃本轮
```

### 2.3 止盈平仓盘口恢复确认

该逻辑只用于 `take_profit`，不用于 `margin_close` / `negative_funding_exit` / `funding_count`。平仓侧观察：

- Binance spot bid 深度（现货卖出会吃 bid）
- Gate future ask 深度（空头买回会吃 ask，按 `quanto_multiplier` 换算为 USDT）
- `close_vwap_basis_bps` 波动与回弹
- `spot_close_coverage` 与 `future_close_coverage`

平仓与开仓不同：已有仓位不能无限等待。因此 `trade.close_resiliency.max_wait_sec` 超时后会放行到最终旁路，由旁路重新确认平仓仍有收敛利润。

```
take_profit + valley rebound
  → CLOSE_RESILIENCY_WAIT
  → 条件恢复：进入最终风控旁路
  → 等待超时：进入最终风控旁路（保底）
  → basis 回到开仓基差以上 / 回弹过大：取消本轮止盈，回到 holding
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.close_resiliency.enabled` | true | 是否启用止盈平仓盘口恢复确认 |
| `trade.close_resiliency.window_sec` | 1.5 | 盘口恢复观察窗口 |
| `trade.close_resiliency.min_samples` | 3 | 窗口内最少样本 |
| `trade.close_resiliency.min_recovery_ratio` | 0.55 | 当前深度相对监控起点的最小恢复比例 |
| `trade.close_resiliency.max_spread_widen_bps` | 10 | spread 最大扩大幅度 |
| `trade.close_resiliency.max_basis_volatility_bps` | 8 | 窗口内平仓基差最大波动 |
| `trade.close_resiliency.max_basis_rebound_bps` | 8 | 等待期间平仓基差最大回弹 |
| `trade.close_resiliency.min_hold_sec` | 0.3 | 恢复条件连续满足时长 |
| `trade.close_resiliency.max_wait_sec` | 1.5 | 等待超时后交给最终旁路判定 |
| `trade.close_resiliency.coverage_threshold` | 0.6 | 平仓双边覆盖上限 |

### 2.4 平仓最终风控旁路

```
① 单标的盘口读取
② 盘口新鲜度硬约束：now_ts − last_update_time ≤ max_orderbook_lag_ms（gate / spot 双侧各自判定）
③ 重算平仓 VWAP 基差
④ 盘口覆盖不超过 close_resiliency.coverage_threshold
⑤ 止盈路径：收敛仍存在、回弹未超过 50% 收敛空间、动态净收益仍 ≥ dynamic_take_profit_bps
⑥ 风险路径：只检查新鲜度/同步/深度，不要求当前盈利
   通过：用这份数据下单 + 将 (gate_lag_ms, spot_lag_ms) 记入鲜度槽供平仓原因拼接
   失败：清谷底状态，下一轮重判
   异常：退化放行
```

该函数所有拦截 / 通过分支均会输出详细日志（含时间戳 / basis / lag 等）供复盘。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.close.max_orderbook_lag_ms` | 200 (ms) | 同上 |

> **不走旁路的场景**：`margin_close`（紧急平仓）。其他风险退出会走轻量旁路，避免用陈旧盘口或过高覆盖率下单。

### 2.5 平仓执行模式

所有正向平仓都先处理 Gate 期货空头，再按 Gate 实际成交数量和
`spot_open_qty / future_open_qty` 的持仓比例，使用 Binance 现货市价单卖出对应数量：

平仓订单的 `target_amount` 仅用于审计展示，按目标数量乘以下单时该腿的平仓
VWAP/一档价格估算；风险平仓缺少盘口时退回历史开仓价估算，不读取当前单笔开仓配置。
零数量或缺少参考价的拒单记录使用非空零值兜底，不能让审计字段阻断风险处置落库。
部分成交后若一条腿已经归零而另一条腿仍有余量，即使余量小于交易步长，也必须标记为
`desynced` 并转交对账兜底，不得继续作为普通 `holding` 进入保证金或止盈平仓路径。

- 普通止盈和所有负资金费经济性退出使用 Gate `reduce_only` 非零保护价 IOC；保护价以该笔持仓真实待平数量的
  `future_close_vwap` 加允许滑点计算，不等待 maker；
- Gate 保护 IOC 为 `price=保护上限 + tif=ioc`。零成交时不提交 Binance；部分成交时
  Binance 只卖出同比例现货，剩余部分继续作为平衡持仓保留；Binance 按 `step_size`
  向下截断产生的不足一个步长差异按不可成交尘埃处理，不误报为断腿；
- 保证金、下架等硬风险平仓和手动平仓继续使用 Gate 市价语义 `price=0 + tif=ioc`，不附加保护价格，
  优先快速完整退出；
- Gate 已成交而 Binance 失败，或两腿成交比例不一致时，立即标记 `desynced` 并触发对账。任一腿只要产生真实减仓，就消费当前 Gate 风险快照并停止本轮；即使本地落库异常也必须保留成交数量并等待新快照，该币种在断腿解除前不再进入任何平仓路径。
- Gate 已成交后的 Binance 现货卖出如果被价格区间规则拒绝，系统仅对尚未成交的剩余数量做最多 `4` 次短退避重试；每次使用唯一客户订单号。请求超时或连接中断时必须先查询原订单状态，状态未知则停止，禁止盲目重复下单。
- 平仓调用成交服务使用独立 `120s` 客户端超时，覆盖 Gate 下单及 Binance 内部下单与查单的最坏时长，确保币种级减仓执行权不会在成交服务仍重试时提前释放。
- 上述抗拒单与对账兜底都只允许继续卖出现货或以 Gate `reduce_only` 买回多余空头，不允许买入缺失现货，也不允许重开 Gate 空头。重试仍未完成时，本地只扣减真实成交数量，剩余仓位保持 `desynced` 交给下一次新快照复核。若交易所已产生真实成交但本地持久化失败，平仓执行器按币种和原持仓 ID 建立进程内隔离，并尽力单独把 `desynced` 隔离状态写回持仓表以覆盖服务重启；持仓对象重新加载或 Gate 风险快照刷新都不能解除，只有对账将原持仓标记为 `resolved` 或确认原持仓已关闭后才恢复该币种的平仓扫描。
- 任意平仓原因在下单前都必须检查 Binance 现货腿最低名义金额。低于门槛时两腿都不下单、不标记 `desynced`，只保留为低名义残仓；MMR 恢复会跳过该笔并继续选择可实际减仓的仓位。
- 若历史执行已经导致 Gate 腿归零、Binance 只剩低于最低名义金额的现货，且订单账本与两家交易所的币种级汇总完全一致，对账会立即将该笔持仓标记为 `closed`，清除 Gate 缺腿风险，并按已发生的真实成交保守计入已实现收益。未兑换现货暂按零回收价值处理，同时以 `post_close_spot_dust_pending` 继续纳入币种级现货敞口，不得因持仓已关闭而从对账中消失。
- 两腿按同一比例成交、但现货步长截断导致 Gate 已归零且只剩低于最小名义金额的
  Binance 尘埃时，对账按同币种聚合全部 holding 记录；只要订单账与两家交易所余额完全
  一致、聚合现货与 Gate 空头两腿均低于最小成交额，就自动先归零 Gate 小额空头，再复用
  Binance 小额资产转 BNB 接口并将对应本地持仓闭合；存在额外手动余额、锁定余额、账实
  数量差异或任一腿聚合名义达到门槛时不会触发兑换。兑换成交后会补写尘埃现货平仓订单、
  重算已实现收益并清除 `post_close_spot_dust_pending`。
- Gate 二次补平已经成交、但 Binance 因最小名义金额拒单时，必须立即按实际 Gate
  成交量扣减本地 `future_open_qty/future_open_contracts`，不能只标记 `desynced`。
- 持仓对账页的“小额兑换”用于处理上述低名义残余。每次执行前重新拉取两家交易所，
  并要求本地残余、订单成交账本、Binance 可用余额、Gate 空头及合约乘数全部一致，且
  两腿都低于最小成交额；先 `reduce_only` 市价归零 Gate 小额空头，再调用 Binance
  小额资产转 BNB。成交会按残余数量分摊写入订单审计，相关历史持仓转为 `closed` 并
  重新计算订单级已实现盈亏。任一条件不一致时只返回拒绝原因，不执行交易。

同币种批量止盈继续保留首笔执行质量保护：首笔真实平仓基差相对 `pre_gate` 的不利滑点超过
`close_quality_guard.max_close_basis_slip_bps` 时，暂停该币种后续自动止盈。

平仓成功后，原因会追加：

```
保护IOC(future_buy≤...,slip≤5.0bps)
平仓基差对比(trigger=...,pre_gate=...,actual=...)
```

其中 `trigger` 是状态机触发时看到的平仓基差，`pre_gate` 是下单前旁路重算 VWAP 基差，`actual` 是成交后按真实成交价计算出的基差。

### 2.6 平仓失败冷却

`trade.close.cooldown_sec = 60s`，普通平仓失败后该标的 60s 内不重试；保证金危险平仓不写入也不读取该冷却，失败后在下一轮继续尝试，并用持仓级 in-flight 锁避免并发重复提交。

## 3. 保证金风控（全仓）

### 3.1 口径

```
account_mmr_pct = Gate accounts 接口 cross_mmr × 100
available_ratio = Gate可用资金 / Gate账户权益 × 100
```

本地“账户权益 / 全部维持保证金”只用于审计，不覆盖 Gate 官方 `cross_mmr`。账户 `cross_initial_margin` 和合约 `initial_margin` 只用于展示初始保证金占用；系统不再发布“最弱合约 MMR”、合约权益或单仓 MMR。单合约 `position.margin` 不参与正向策略；全仓资金由账户共享。

### 3.2 风控层级

| 层级 | 阶段 | 阈值 | 行为 |
|------|------|------|------|
| 预防 | 开仓 | Gate `warning/danger` | 禁止所有正向新开仓 |
| 资金缓冲 | 开仓 | Gate 可用资金至少 15% | 低于阈值拒绝开仓 |
| 监控 | 持仓 | 账户 MMR + 最近强平距离 | 持续刷新账户级风险 |
| 自动补资 | 资金 | MMR <= 500% | 正向开仓开关开启时，按目标 700% 创建 Binance → Gate 账户级划转 |
| 盈利释放 | 平仓 | MMR <= 350% 且自动评估确认资金不足 | 一次性许可平一笔预计整组净盈利仓位；真实释放 Binance 资金后立即重算 |
| 分步恢复 | 平仓 | MMR <= 300% | 在有效缓解 MMR 的候选中优先预计损失较小的完整套利仓位；释放现货资金后立即重算自动划转 |
| 最高安全 | 平仓 | MMR <= 200% 或强平距离 <= 300bps | 不按盈亏，按强平距离和维持保证金释放能力处理；释放现货资金后立即重算自动划转 |

每个 Gate 官方新鲜风险快照最多成功平一个本地完整套利仓位，任一腿失败立即停止本轮。`<=300%` 启动的恢复事件会持续到 MMR 回到 `500%`；`<=200%` 仍不执行跨持仓聚合全平。`100%` 是 Gate 交易所强平的基准线，最终以交易所实际强平价和风控结果为准。

自动划转所需额为 `max(0, Gate维持保证金 * 7 - Gate账户权益) * 1.15`；单次最多使用 Binance Forward 可用资金的 `70%`，且 Binance 至少保留 `max(总资产 * 2%, 50 USDT)`。最低有效额为 `max(100 USDT, Gate维持保证金 * 50%, 交易所最低额)`，不足时不提现并写入铃铛。只有该“资金不足”结果生成的一次性许可允许 `350%` 盈利释放；找到盈利候选并取得币种执行权后才领取，领取期间人工/自动划转均被阻止。拒单或异常释放预约但不立即重算，真实卖出 Binance 现货后立即重算；再次确认不足前不继续释放。关键金额缺失、非有限值、非正维持保证金/Binance 总资产，或负数 Binance Forward 可用余额/交易所最低划转额都会阻断自动补资。自动划转只创建账户级资金迁移任务，不恢复逐币追保或单仓 MMR。

### 3.3 集中度与风险边界

- 单币集中度使用等额 Binance 现货名义金额判断，普通上限 15%，优质加仓上限 25%。高基差通道也可使用 25% 上限，但必须完整满足高基差准入，且当前基差相对已有仓位加权入场基差至少改善 20bps。
- Gate 全仓不再计算逐币保证金集中度。
- Gate 全仓风险会影响账户内所有正向仓位，因此 warning/danger 状态会统一禁止新开仓。
- 正向策略没有逐币追保逻辑；账户可用资金本身就是共享风险缓冲。MMR 自动补资只把 Binance 账户级资金迁移到 Gate Forward 全仓账户。

## 4. 数据流

```
WebSocket（Binance @depth20@100ms + Gate futures.obu 50档订阅/前20档输出）
    ↓
本地 OrderBook
    ↓
合并 → 计算对冲指标(VWAP / coverage)
    ↓
┌─ 实时 PnL（5s）─────────────────┐
│ 浮动盈亏 + 资金费 + 爆仓价 + 距爆仓
│ → 推送前端 + 更新 _holding_liq_distance
└──────────────────────────────────┘
    ↓
┌─ 开仓循环（0.2s）──────────────┐
│ 风控 → 冷却 → 峰值回落+sustain → 盘口恢复 → 旁路 │
│ → 调用成交引擎下单                  │
└─────────────────────────────────┘
    ↓
┌─ 平仓循环（0.2s）──────────────┐
│ P0 独立全仓危险路径 → 普通风险/止盈路径 │
│ → P2 止盈+谷底+盘口恢复+旁路   │
│ → P3 累计资金费                │
│ → 调用成交引擎平仓            │
└──────────────────────────────────┘
```

热路径约束：开仓/平仓循环（0.2s）主体仍是内存读取 + 纯计算 + ExecutorClient 下单；REST 调用只发生在候选信号进入状态机时，以及实盘最终旁路下单前刷新 funding 时，不对 250 个订阅标的逐 tick 拉取。

### 5.2 执行模式

当前实盘开仓优先采用 `Gate future maker + Binance spot taker`：

1. 策略状态机仍先完成 funding-adjusted entry、funding carry / momentum / rebound、resiliency、旁路风控。
2. 满足条件后，Gate future 以 future ask1 发送 post-only maker 卖单。
3. `ttl_ms` 内未成交则撤单；若 `pre_gate >= entry_floor + fallback_min_buffer_bps` 且保护价可用，Gate future 转保护 IOC 卖出兜底。
4. 如果 Gate future maker 或 fallback IOC 部分/全部成交，系统按实际成交数量提交 Binance spot 市价买入。
5. 开仓原因追加执行统计：`future_maker`、`fill`、`wait`、`maker_px`、`future_px`、`spot_px`、`improve`、`fallback`、`fallback_filled`。
6. `mi_trade_order` 会持久化 `liquidity_role`、`fee_rate`、`fee_amount`、`fee_asset`、`fee_amount_usdt`、`exchange_order_id`；持仓监控优先按订单级 `fee_amount_usdt` 计算，缺失时只对缺失腿按订单级 `fee_rate` 估算，不使用合约公开费率代表账户费率。

平仓方向相反：普通止盈 Gate future 发送 reduce-only 保护 IOC 买单；风险与手动平仓发送
reduce-only 市价买单。成交后统一按 `spot_open_qty / future_open_qty` 折算实际 Binance
spot 市价卖出数量。

## 7. VWAP 计算说明

- VWAP（Volume Weighted Average Price）是市价单按盘口逐档成交的真实加权均价
- **VWAP 不需要满足交易所 tick_size**（那是限价单约束）
- 基差计算保留 VWAP 真实精度，不做 floor 截断
- 实际成交后用 `exec_price` 重算基差并写入 DB，统一为实际成交口径
