# 交易逻辑说明

## 策略概述

跨交易所资金费率套利：**Binance 现货买入 + Gate 永续合约做空**，赚取正资金费率收入，并在基差收敛时止盈平仓。

- 保证金模式：**逐仓**（每个合约仓位独立保证金，风险隔离）
- 决策频率：开仓循环 0.2s / 平仓循环 0.2s / 实时PnL与风控刷新 5s
- 模式开关：`trade.mode` ∈ {`virtual` / `testnet` / `live`}

### 标的分层

`mi_base_asset.strategy_tier` 用于区分标的质量：

| 分层 | 当前规则 | 策略含义 |
|------|----------|----------|
| A | Binance spot 24h 成交额 ≥ 1000万 USDT 且 Gate futures 24h 成交额 ≥ 500万 USDT | 主交易池，优先允许 momentum；未命中 momentum 时也必须走 pullback + resiliency + rebound |
| B | Binance spot 24h 成交额 ≥ 100万 USDT 且 Gate futures 24h 成交额 ≥ 50万 USDT | 可交易观察池，禁用 momentum，走 pullback + resiliency + rebound |
| C | 其他 | 谨慎池，默认不进入 WebSocket 订阅，不参与自动开仓 |

当前分层是“流动性分层”。后续积累 `signal_basis_bps / pre_gate_basis_bps / actual_basis_bps` 后，可以把 `execution_drift_p80 = pre_gate_basis_bps - actual_basis_bps` 加入分层：A 级要求 drift_p80 更小，C 级即使成交量达标也可因真实滑点差而降级。

WS 订阅由 `orderbook.strategy_tiers` 控制，当前默认 `[A, B]`。因此 C 级标的不会进入 Gate OBU 或 Binance depth20 订阅，也不会进入合并盘口、广播、VWAP 快照和开仓扫描热路径。

开仓通道由 tier 继续分流：`trade.momentum_open.allowed_tiers = [A]`，所以只有 A 级能走 momentum；`trade.rebound_open.allowed_tiers = [A, B]`，所以 A 级未命中 momentum 时、以及所有 B 级，都必须等待峰值回落、盘口恢复和回调后再突破。

开仓入口不再只看 `open_basis >= p20`。系统会先计算一个统一的 `entry_floor`：它把 24h funding 的一部分、全程手续费、滑点缓冲和 p20 位置合并到同一套门槛里。后续 risk check、momentum、resiliency、rebound、pre-gate 和 execution guard 都使用这个 `entry_floor`，避免入口允许、后面又被旧 p20/盈利性守卫误杀。

## 1. 开仓流程

入口：[`TradingExecutor.check_and_open()`](file:///Users/jeffrey/Documents/MyProject/Arbitrage-Mi/src/calc/trading_executor.py)
触发频率：`trade.open.check_interval_sec = 0.2s`

### 1.1 全链路总览

```
每轮 0.2s 触发
    │
    ├─ 0. 数据完整性检查（盘口缺失 → 清状态跳过）
    ├─ 1. 风控检查（_pass_risk_check，下面 §1.2）
    ├─ 2. 冷却/降噪检查（开仓冷却 / 超时冷却 / 拒单冷却 / 回弹超时 / 信号噪音 / 执行漂移）
    ├─ 3. 开仓通道：基差 ≥ entry_floor 后二选一
    │   首次入场：实时校验 24h 资金费率（REST）；拿到实时值后覆盖本轮信号 funding 口径
    │   A. 动量通道（可选）：达到 entry_floor + buffer + 短窗口上升 + 盘口覆盖良好 → 直接进入最终旁路
    │   B. 回落通道：基差从峰值回落 ≥ pullback_pct + sustain 持续确认 → 进入盘口恢复确认
    │      A 未命中 momentum、以及 B 级标的：盘口恢复后不立刻下单，继续等待二次突破；
    │      若已明显高于 entry_floor 并稳定保持，则可走强安全垫确认
    │   回落通道监控超时（基差长期不回落）：放弃本轮 + 进入 timeout_cooldown_sec 冷却
    │
    ├─ 4. 盘口恢复确认（orderbook resiliency，下面 §1.4）
    │   Gate future bid + Binance spot ask 深度恢复 / spread 未扩大 / basis 稳定 / 双边覆盖达标
    │
    ├─ 5. 最终风控旁路（_pre_execution_gate，下面 §1.5）
    │   单标的最短链路重新校验：盘口新鲜度 + 实时 funding 重算 entry_floor + 覆盖率
    │   执行保护：pre_gate 基差必须保留 entry_floor / 峰值衰减安全垫
    │
    └─ 6. 下单：调用 ExecutorClient → 持久化订单/持仓/信号，并记录 signal/pre_gate/actual 三段基差
```

### 1.2 风控检查（_pass_risk_check，全部通过才进入下一步）

| # | 检查项 | 配置项 | 默认值 |
|---|--------|--------|--------|
| 0 | 同标的持仓数 < 上限 | `trade.open.max_positions_per_asset` | 6 |
| 1 | 该标的现有持仓距爆仓距离 ≥ 警戒线 | `margin.warning_pct` | 15% |
| 2 | `open_amount_usdt` ≥ 现货最小名义价值 | `trade.open.amount_usdt` | 10 USDT |
| 3 | 24h 资金费率(bps) ≥ 下限 | `trade.open.min_funding_rate_bps` | 0 bps |
| 4 | 开仓盘口覆盖率 ≤ 阈值 | `trade.open.orderbook_coverage_threshold` | 0.6 |
| 5 | 开仓基差 ≥ `entry_floor` | `trade.funding_adjusted_entry.*` + `mi_vwap_basis_threshold.open_basis_p20` | 见下 |
| 6 | 旧模式盈利性守卫：开仓基差 > 平仓基差阈值 + 全部手续费（仅 `funding_adjusted_entry.enabled=false`） | `trade.vwap.close_threshold_percentile` | `close_basis_p20` |
| 7 | 期货 24h 成交量 ≥ 阈值 | `trade.filter.min_future_volume_24h_usdt` | 50000 |
| 8 | 现货 24h 成交量 ≥ 阈值 | `trade.filter.min_spot_volume_24h_usdt` | 100000 |

**统一入场门槛公式**：

```
expected_funding_bps = funding_24h_bps * funding_capture_ratio
carry_floor = min_expected_edge_bps + fee_full_bps + slippage_buffer_bps - expected_funding_bps
timing_floor = open_basis_p20 - min(max_funding_discount_bps, funding_24h_bps * discount_ratio)
entry_floor = max(carry_floor, timing_floor)

如果 funding_24h_bps < strong_funding_24h_bps:
    entry_floor = max(entry_floor, open_basis_p20)
```

含义：funding 很厚时，可以比 p20 略早一点进入，但最多只放宽 `max_funding_discount_bps`；funding 不厚时，不允许因为 p20 为负而低质量刷信号。

### 1.3 开仓通道状态机

系统现在有两个开仓通道，但后续共用同一套最终旁路、执行器、持久化逻辑。

#### 1.3.1 动量开仓通道（默认关闭）

动量通道用于你提到的“判断超阈值且处于上升期且盘口好的话直接开”。它不等待回调，也不走开仓 resiliency；它只负责把强势上升信号送到最终旁路，由旁路在下单前重新确认基差、盘口鲜度、覆盖率和盈利性。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.momentum_open.enabled` | true | 是否启用动量开仓通道 |
| `trade.momentum_open.allowed_tiers` | [A] | 允许走动量通道的分层；B 不在其中 |
| `trade.momentum_open.window_sec` | 1.2 | 默认短窗口；A 级由 `tier_overrides.A.window_sec=1.0` 覆盖 |
| `trade.momentum_open.min_samples` | 3 | 动量判断最少样本 |
| `trade.momentum_open.min_rise_bps` | 3 | 窗口内基差最小上升幅度 |
| `trade.momentum_open.min_basis_buffer_bps` | 8 | 默认当前基差需高于 p20 的额外安全垫；A 级覆盖为 6 |
| `trade.momentum_open.safety_bps` | 8 | 旧模式盈利性守卫额外安全垫；A 级覆盖为 6 |

状态机：
```
基差 ≥ entry_floor + buffer
短窗口样本数 ≥ min_samples
当前基差 - 窗口首个基差 ≥ min_rise_bps
当前基差接近窗口最高点（不是明显回落中）
覆盖率 ≤ coverage_threshold
实时费率校验通过
              → 创建 signal(trigger_type='momentum') → 最终风控旁路
```

#### 1.3.2 峰值回落 + sustain 开仓确认

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.peak_pullback.pullback_pct` | 0.05 | 从峰值回落 5% 触发开仓 |
| `trade.peak_pullback.sustain_sec` | 1.5 | 峰值监控最低持续秒数（过滤脉冲信号） |
| `trade.peak_pullback.monitor_timeout_sec` | 60 | 监控超时（基差长期不回落 → 放弃本轮+进入冷却，不开劣质单） |
| `trade.peak_pullback.timeout_cooldown_sec` | 300 | 监控超时后冷却（重新进入监控前的等待） |

状态机（`_pass_peak_check`）：
```
基差首次 ≥ entry_floor → 实时校验24h费率(API) → 创建信号 + 记录峰值
基差更高        → 更新峰值
elapsed ≥ monitor_timeout_sec → 放弃本轮(信号 'monitor_timeout') + 进入 timeout_cooldown 冷却
基差 ≤ 峰值×(1-pullback_pct) 且 elapsed ≥ sustain_sec
              → 进入 RESILIENCY_WAIT（pullback）
RESILIENCY_WAIT → 后续每轮持续采样盘口恢复，不再反复要求 pullback 形态成立
恢复通过        → B 级进入 REBOUND_WAIT；其他未启用回弹确认的 tier 进入最终旁路
REBOUND_WAIT    → 基差从回调低点再次上行突破，或强安全垫稳定保持 → 最终风控旁路
回落但sustain不足 → 仅拦截本轮，状态保留到下轮重判
基差跌回 entry_floor 下 / 数据中断   → 清除状态
```

> **设计原则**：回落 + sustain 双重叠加，配合旁路 `lag_ms` 新鲜度硬约束。B 级新增 `rebound` 是为了避免“回调后第一口流动性继续衰减”：先确认盘口恢复，再等基差从回调低点重新上行，确认二次拉升后才开仓。

### 1.4 开仓盘口恢复确认（orderbook resiliency）

峰值回落通过后不立即下单，而是确认被冲击的开仓侧盘口已经恢复。该逻辑由 `calc/orderbook_resiliency.py` 统一实现，开仓侧观察：

- Binance spot ask 深度（现货买入会吃 ask）
- Gate future bid 深度（合约做空会吃 bid，按 `quanto_multiplier` 换算为 USDT）
- spot/future bid-ask spread 是否相对窗口起点扩大
- 最近窗口内 `open_vwap_basis_bps` 是否稳定
- `spot_open_coverage` 与 `future_open_coverage` 是否都在阈值内

状态机：
```
pullback confirmed
  → RESILIENCY_WAIT
  → 样本数不足 / 深度未恢复 / spread过宽 / basis波动过大 / coverage未恢复：继续等待
  → 等待超时：信号记为 gate_rejected，原因以 resiliency: 开头，放弃本轮
  → 条件连续满足 min_hold_sec：B 级进入回调后再突破等待，其他 tier 进入最终风控旁路
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.resiliency.enabled` | true | 是否启用开仓盘口恢复确认 |
| `trade.resiliency.window_sec` | 3.0 | 盘口恢复观察窗口 |
| `trade.resiliency.min_samples` | 2 | 窗口内最少样本 |
| `trade.resiliency.min_recovery_ratio` | 0.65 | 当前深度相对监控起点的最小恢复比例 |
| `trade.resiliency.max_spread_widen_bps` | 8 | spot/future spread 最大扩大幅度 |
| `trade.resiliency.max_basis_volatility_bps` | 6 | 窗口内开仓基差最大波动 |
| `trade.resiliency.min_hold_sec` | 0.4 | 恢复条件连续满足时长 |
| `trade.resiliency.max_wait_sec` | 5.0 | 等待恢复超时后放弃本轮信号 |

### 1.4.1 回调后再突破确认（rebound open）

A/B 级标的在 `pullback + resiliency` 通过后不会立刻开仓，而是进入 `REBOUND_WAIT`。A 级只有命中 momentum 时才能跳过这一步。`REBOUND_WAIT` 有两条通过路径：

**普通二次突破路径**：

```
resiliency passed
  → 记录回调低点 floor
  → 当前基差从 floor 至少回升 min_rise_bps
  → 当前样本相对上一样本仍向上 min_slope_bps
  → 当前基差 ≥ entry_floor + min_basis_buffer_bps
  → 最终风控旁路
```

**强安全垫路径**：

```
resiliency passed
  → 当前基差 ≥ entry_floor + strong_cushion_bps
  → 连续保持 strong_cushion_min_hold_sec
  → 最终风控旁路
```

强安全垫路径用于 SAHARA 这类情况：funding 和当前基差都很厚，但回调后基差横住，没有再额外拉升 4bps。它不绕过最终旁路和 execution guard，只是不再机械要求“从低点再涨 + 当前样本继续向上”。

成功触发强安全垫路径时，`mi_trade_signal.trigger_type` 记录为短码 `rebound_strong`。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.rebound_open.enabled` | true | 是否启用回调后再突破确认 |
| `trade.rebound_open.allowed_tiers` | [A, B] | A 未命中 momentum 时、以及 B 级，都使用回弹确认 |
| `trade.rebound_open.min_rise_bps` | 4 | 从回调低点至少回升多少 bps |
| `trade.rebound_open.min_slope_bps` | 0.5 | 当前样本相对上一样本仍需向上 |
| `trade.rebound_open.min_basis_buffer_bps` | 4 | 当前基差需高于 entry_floor 的额外安全垫 |
| `trade.rebound_open.max_wait_sec` | 5.0 | 盘口恢复后最多等待普通二次突破多久 |
| `trade.rebound_open.strong_cushion_bps` | 20 | 当前基差高于 entry_floor 多少 bps 后进入强安全垫确认 |
| `trade.rebound_open.strong_cushion_min_hold_sec` | 1.0 | 强安全垫连续保持多久才确认 |
| `trade.rebound_open.strong_cushion_max_wait_sec` | 8.0 | 强安全垫活跃时最多等待确认多久 |

等待期间如果基差跌回 `entry_floor` 以下，信号记为 `conditions_lost`；超过等待时间仍未二次突破、也未完成强安全垫保持，信号记为 `monitor_timeout`，并进入短冷却，防止同一段盘口状态反复刷信号。timeout 原因会记录 `floor/current/rise/slope/min_basis/entry_floor/strong_cushion/strong_hold/timeout`，用于判断到底是形态没起来，还是强安全垫保持时间不够。

### 1.4.2 执行质量保护（execution guard）

最终旁路通过后、下单前，还会检查 pre-gate 基差是否留有足够安全垫：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.execution_guard.enabled` | true | 是否启用下单前执行保护 |
| `trade.execution_guard.min_profit_buffer_bps` | 15 | 旧模式字段；新模式不再单独使用盈利性守卫 |
| `trade.execution_guard.min_p20_buffer_bps` | 3 | 新模式下表示 pre_gate 需高于 entry_floor 的额外安全垫 |
| `trade.execution_guard.max_peak_decay_bps` | 45 | pre_gate 相对峰值最多允许衰减多少 bps |

该保护不能替代真实 IOC/限价执行，但能先过滤“信号仍成立、实际已经太弱”的下单。

### 1.4.3 开仓基差审计字段

为了定位“触发时很好、成交时变差”的漂移，系统会同时记录三段基差：

| 字段 | 记录位置 | 口径 |
|------|----------|------|
| `signal_basis_bps` | `mi_trade_signal` / `mi_trade_order` / `mi_trade_position` / 开仓原因 | 触发时看到的开仓 VWAP 基差 |
| `pre_gate_basis_bps` | 同上 | 下单前最终旁路用最新盘口重算的基差 |
| `actual_basis_bps` | 同上 | 成交后按真实成交价计算的基差 |

成功开仓的原因里会追加：`基差对比(signal=...,pre_gate=...,actual=...)`，并同步写入 `mi_trade_signal.exit_reason`，所以交易信号页的“结束原因”列也能直接查看开仓复盘信息。

开仓原因里的 funding 口径以实时值为准：`carry(funding24h=...)`、`实时24h费率...`、订单表 `funding_rate_24h` 都使用最近一次 Gate 实时合约接口返回值。若实时值与缓存元数据不同，会额外记录 `缓存24h费率...(偏移...bps)`，方便判断是 Gate funding 快速变化，还是元数据刷新滞后。

### 1.5 最终风控旁路（_pre_execution_gate）

确认信号后、下单前的最后一道闸。**单标的最短链路**重读盘口、重算指标。

```
① 单标的盘口读取：gate_manager.get_orderbook(contract) + spot_manager.get_orderbook(symbol)
② 盘口新鲜度硬约束：now_ts − last_update_time ≤ max_orderbook_lag_ms（gate / spot 双侧各自判定）
③ 合并 + VWAP 基差重算
④ 基差 ≥ entry_floor？覆盖率达标？
   通过：用这份数据下单（数据=校验数据，零缝隙）+ 将 (gate_lag_ms, spot_lag_ms) 记入最近一次鲜度槽供原因拼接
   失败：信号标记 gate_rejected，清状态
   异常：退化为放行（不阻塞热路径）
```

> ② **鲜度闸** 是破除“旁路与 sustain 同源缺陷”的核心实践：以本地接收时刻（`last_update_time`）为准，反映“现在距上次收到 WS 增量多久”。交易所推送的 `update_time` 不可靠（快照重建后会“看起来很新”），本地接收时刻才是最接近客观事实的新鲜度判定。

该函数所有拦截分支均会输出详细日志（含时间戳、basis、lag等），通过分支也会打一行 `开仓旁路通过 | ...` 供复盘。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.open.max_orderbook_lag_ms` | 1000 (ms) | 当前为虚拟盘观察期临时放宽；后续实盘可收紧 |

### 1.6 冷却与降噪

| 触发场景 | 配置项 | 默认值 |
|---------|--------|--------|
| 同标的开仓后 | `trade.open.cooldown_sec` | 60 s |
| 峰值监控超时（放弃本轮，不开仓） | `trade.peak_pullback.timeout_cooldown_sec` | 300 s |
| 被交易所拒单后 | `trade.open.reject_cooldown_sec` | 300 s |
| 回弹等待超时 | `trade.rebound_timeout_cooldown.cooldown_sec` | 45 s |
| 单标的近 60 分钟信号过密但几乎不开仓 | `trade.asset_noise_cooldown.*` | 30 min |
| 成交后 `pre_gate_basis_bps - actual_basis_bps` 过大 | `trade.execution_drift_cooldown.*` | 6 h |

这些冷却只拦截新信号，不会中断已经进入状态机的信号。

## 2. 平仓流程

入口：[`ClosingExecutor.check_and_close()`](file:///Users/jeffrey/Documents/MyProject/Arbitrage-Mi/src/calc/closing_executor.py)
触发频率：`trade.close.check_interval_sec = 0.2s`

### 2.1 平仓优先级（命中即触发）

| 优先级 | 触发条件 | 配置 | 是否走旁路 |
|-------|---------|------|----------|
| 0（最高） | **保证金爆仓风控**：距爆仓距离 < `margin.close_threshold_pct`(5%) | `margin.close_threshold_pct` | 否（紧急） |
| 1 | **结算前负资金费风险**：临近结算且下一期预计大额负 funding，会显著恶化净收益 | `pre_funding_guard_*` | 是，风险旁路 |
| 2 | 资金费支付次数 ≥ 上限 | `trade.close.max_funding_payments`(30) | 是，风险旁路 |
| 3 | **固定净止盈**：收敛收益 + 已收资金费 - 全部手续费 ≥ 固定 bps | `trade.close.fixed_take_profit_bps`(100) | 是，且先走盘口恢复 |
| 4 | **累计资金费支出超阈值**（仅当当前24h费率<0时） | `trade.close.funding_cost_tolerance_ratio`(0.2) `funding_cost_min_threshold_bps`(10) | 是，风险旁路 |

**止盈公式**：
```
spread_profit_bps = open_spread_bps - current_spread_bps
funding_earned_bps = funding_pnl_bps    # 已收资金费 bps（含正负）
net_profit_bps = spread_profit_bps + funding_earned_bps - fee_full_bps
触发: net_profit_bps ≥ fixed_take_profit_bps
```

当前默认 `fixed_take_profit_bps = 100`。如果下一期预计正资金费足够厚，且距离结算在 `positive_funding_hold_window_min` 内，即使固定净止盈已达标，也会暂缓到结算后再重新评估。

**结算前负资金费风险公式**：
```
next_funding_bps = funding_rate_24h × 10000 / funding_periods_per_day
projected_net_bps = net_profit_bps + next_funding_bps
触发:
  距结算 <= pre_funding_guard_window_min
  且 next_funding_bps <= -pre_funding_guard_large_negative_bps
  且 projected_net_bps < pre_funding_guard_min_projected_profit_bps
```

> `take_profit_mode=legacy_p40` 时仍可回退到旧 p40 倍数止盈，但当前实盘配置使用固定净 bps。

**累计资金费超阈值公式**（条件3）：
```
convergence_space = open_basis_p20 - close_basis_p20
effective_space   = max(convergence_space, funding_cost_min_threshold_bps)
threshold         = effective_space × funding_cost_tolerance_ratio
触发: abs(funding_pnl_bps) ≥ threshold  且  funding_rate_24h < 0
```

### 2.2 谷底反弹确认（仅止盈使用）

| 配置项 | 默认值 |
|--------|--------|
| `trade.valley_rebound.rebound_pct` | 0.10 |
| `trade.valley_rebound.monitor_timeout_sec` | 60 |

状态机：
```
止盈首次满足 → 记录 valley_bps + start_time
基差更低     → 更新 valley
基差 ≥ valley + (open_spread_bps - valley) × rebound_pct → 反弹确认平仓
elapsed ≥ timeout → 直接平仓（保底）
止盈不再满足 → 清除状态，放弃本轮
```

### 2.3 止盈平仓盘口恢复确认

该逻辑只用于 `take_profit`，不用于 `margin_close` / `pre_funding_risk` / `funding_count` / `funding_cost_exceeded`。平仓侧观察：

- Binance spot bid 深度（现货卖出会吃 bid）
- Gate future ask 深度（空头买回会吃 ask，按 `quanto_multiplier` 换算为 USDT）
- `close_vwap_basis_bps` 波动与回弹
- `spot_close_coverage` 与 `future_close_coverage`

平仓与开仓不同：已有仓位不能无限等待。因此 `trade.close_resiliency.max_wait_sec` 超时后会放行到最终旁路，由旁路重新确认平仓仍有收敛利润。

```
take_profit + valley rebound
  → CLOSE_RESILIENCY_WAIT
  → 条件恢复：进入最终风控旁路
  → 等待超时：进入最终风控旁路（保底）
  → basis 回到开仓基差以上 / 回弹过大：取消本轮止盈，回到 holding
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.close_resiliency.enabled` | true | 是否启用止盈平仓盘口恢复确认 |
| `trade.close_resiliency.window_sec` | 1.5 | 盘口恢复观察窗口 |
| `trade.close_resiliency.min_samples` | 3 | 窗口内最少样本 |
| `trade.close_resiliency.min_recovery_ratio` | 0.55 | 当前深度相对监控起点的最小恢复比例 |
| `trade.close_resiliency.max_spread_widen_bps` | 10 | spread 最大扩大幅度 |
| `trade.close_resiliency.max_basis_volatility_bps` | 8 | 窗口内平仓基差最大波动 |
| `trade.close_resiliency.max_basis_rebound_bps` | 8 | 等待期间平仓基差最大回弹 |
| `trade.close_resiliency.min_hold_sec` | 0.3 | 恢复条件连续满足时长 |
| `trade.close_resiliency.max_wait_sec` | 1.5 | 等待超时后交给最终旁路判定 |
| `trade.close_resiliency.coverage_threshold` | 0.6 | 平仓双边覆盖上限 |

### 2.4 平仓最终风控旁路

```
① 单标的盘口读取
② 盘口新鲜度硬约束：now_ts − last_update_time ≤ max_orderbook_lag_ms（gate / spot 双侧各自判定）
③ 重算平仓 VWAP 基差
④ 盘口覆盖不超过 close_resiliency.coverage_threshold
⑤ 止盈路径：收敛仍存在、回弹未超过 50% 收敛空间、固定净收益仍 ≥ fixed_take_profit_bps
⑥ 风险路径：只检查新鲜度/同步/深度，不要求当前盈利
   通过：用这份数据下单 + 将 (gate_lag_ms, spot_lag_ms) 记入鲜度槽供平仓原因拼接
   失败：清谷底状态，下一轮重判
   异常：退化放行
```

该函数所有拦截 / 通过分支均会输出详细日志（含时间戳 / basis / lag 等）供复盘。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.close.max_orderbook_lag_ms` | 200 (ms) | 同上 |

> **不走旁路的场景**：`margin_close`（紧急平仓）。其他风险退出会走轻量旁路，避免用陈旧盘口或过高覆盖率下单。

### 2.5 平仓执行模式

默认 `trade.execution.future_maker_close.enabled = true`。平仓时 Gate 期货空头买回腿优先使用 `reduce_only + post-only maker`：

- 挂单价：`future bid1`，即买一价，确保不主动吃单；
- `ttl_ms` 内未成交：撤单后若启用 fallback 且保护价可用，转 `reduce_only + 保护IOC` 兜底；仍未成交才放弃，不提交 Binance 现货腿；
- 部分成交：按 Gate future 实际买回数量，以及 `spot_open_qty / future_open_qty` 的持仓比例，提交 Binance 现货市价卖出；
- 成交统计会写入平仓原因，便于复盘 maker 成交率和真实基差改善。
- `margin_close` 与 `manual` 属于强制退出，不走 maker 等待，仍使用保护性 IOC。

如果关闭 `future_maker_close.enabled`，系统会回落到原保护性 IOC 模式：

| 场景 | 配置 | 默认值 |
|------|------|--------|
| 止盈平仓 | `protective_ioc_take_profit_slippage_bps` | 5 |
| 风险平仓 | `protective_ioc_risk_slippage_bps` | 12 |

平仓成功后，原因会追加：

```
平仓基差对比(trigger=...,pre_gate=...,actual=...)
```

其中 `trigger` 是状态机触发时看到的平仓基差，`pre_gate` 是下单前旁路重算 VWAP 基差，`actual` 是成交后按真实成交价计算出的基差。

### 2.6 平仓失败冷却

`trade.close.cooldown_sec = 60s`，平仓失败后该标的 60s 内不重试；保证金爆仓风控不受冷却约束（每轮都检查）。

## 3. 保证金风控（逐仓）

### 3.1 公式

```
initial_margin   = future_open_price × future_open_qty / leverage
total_margin     = initial_margin + margin_topup_total
liq_price        = future_open_price + total_margin / future_open_qty - maintenance_rate × future_open_price
liq_distance_pct = (liq_price - current_future_price) / current_future_price × 100
```

| 参数 | 来源 | 默认值 |
|------|------|--------|
| `leverage` | `margin.leverage` | 2 |
| `maintenance_rate` | `mi_gate_future_contracts.maintenance_rate`，缺失则 `margin.default_maintenance_rate` | 0.005 |
| `margin_topup_total` | `mi_trade_position.margin_topup_total` | 0 |

### 3.2 三层防御

| 层级 | 阶段 | 阈值 | 行为 |
|------|------|------|------|
| 预防 | 开仓 | `margin.warning_pct` (15%) | 该标的距爆仓距离 < 阈值 → 拒新仓 |
| 监控 | 持仓 | — | 5s 计算并推送前端 |
| 主动防御 | 平仓前 | `margin.topup_pct` (12%) | 若仍高于紧急平仓线，自动追保到当前期货名义价值 50% 保证金水平 |
| 应急 | 平仓 | `margin.close_threshold_pct` (5%) | 触发紧急平仓，最高优先级 |

### 3.3 风险隔离

- 单仓爆仓不影响其他仓位（逐仓独立保证金）
- 现货资产物理隔离于另一交易所（Binance）
- 系统在距爆仓 5% 时主动平仓，避免真实爆仓
- 即使主动平仓失败，单仓最大损失 = `open_amount_usdt / leverage`

## 4. 数据流

```
WebSocket（Binance @depth20@100ms + Gate futures.obu 50档订阅/前20档输出）
    ↓
本地 OrderBook
    ↓
合并 → 计算对冲指标(VWAP / coverage)
    ↓
┌─ 实时 PnL（5s）─────────────────┐
│ 浮动盈亏 + 资金费 + 爆仓价 + 距爆仓
│ → 推送前端 + 更新 _holding_liq_distance
└──────────────────────────────────┘
    ↓
┌─ 开仓循环（0.2s）──────────────┐
│ 风控 → 冷却 → 峰值回落+sustain → 盘口恢复 → 旁路 │
│ → 调用成交引擎下单                  │
└─────────────────────────────────┘
    ↓
┌─ 平仓循环（0.2s）──────────────┐
│ P0 爆仓风控 → P1 资金费次数    │
│ → P2 止盈+谷底+盘口恢复+旁路   │
│ → P3 累计资金费                │
│ → 调用成交引擎平仓            │
└──────────────────────────────────┘
```

热路径约束：开仓/平仓循环（0.2s）主体仍是内存读取 + 纯计算 + ExecutorClient 下单；REST 调用只发生在候选信号进入状态机时，以及实盘最终旁路下单前刷新 funding 时，不对 250 个订阅标的逐 tick 拉取。

## 7. VWAP 计算说明

- VWAP（Volume Weighted Average Price）是市价单按盘口逐档成交的真实加权均价
- **VWAP 不需要满足交易所 tick_size**（那是限价单约束）
- 基差计算保留 VWAP 真实精度，不做 floor 截断
- 实际成交后用 `exec_price` 重算基差并写入 DB，统一为实际成交口径
