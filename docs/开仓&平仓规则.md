# 交易逻辑说明

## 策略概述

跨交易所资金费率套利：**Binance 现货买入 + Gate 永续合约做空**，赚取正资金费率收入，并在基差收敛时止盈平仓。

- 保证金模式：**逐仓**（每个合约仓位独立保证金，风险隔离）
- 决策频率：开仓循环 0.2s / 平仓循环 0.2s / 实时PnL与风控刷新 5s
- 模式开关：`trade.mode` ∈ {`virtual` / `testnet` / `live`}

## 1. 开仓流程

入口：[`TradingExecutor.check_and_open()`](file:///Users/jeffrey/Documents/MyProject/Arbitrage-Mi/src/calc/trading_executor.py)
触发频率：`trade.open.check_interval_sec = 0.2s`

### 1.1 全链路总览

```
每轮 0.2s 触发
    │
    ├─ 0. 数据完整性检查（盘口缺失 → 清状态跳过）
    ├─ 1. 风控检查（_pass_risk_check，下面 §1.2）
    ├─ 2. 三类冷却检查（开仓冷却 / 超时冷却 / 拒单冷却）
    ├─ 3. 通道：基差 ≥ p20
    │   首次入场：实时校验 24h 资金费率（一次REST调用，pullback 期间不再调用）
    │   等待：基差从峰值回落 ≥ pullback_pct
    │   sustain 持续确认（持续 sustain_sec，且窗口内 update_count 增量达标）
    │   峰值回落确认（_pass_peak_check）：从峰值回落 ≥ pullback_pct
    │   监控超时（基差长期不回落）：放弃本轮 + 进入 timeout_cooldown_sec 冷却（不开劣质单）
    │
    ├─ 4. 最终风控旁路（_pre_execution_gate，下面 §1.4）
    │   单标的最短链路重新校验：盘口新鲜度 + update_count 增量 + 基差 + 盈利性 + 覆盖率
    │
    └─ 5. 下单：调用 ExecutorClient → 持久化订单/持仓/信号
```

### 1.2 风控检查（_pass_risk_check，全部通过才进入下一步）

| # | 检查项 | 配置项 | 默认值 |
|---|--------|--------|--------|
| 0 | 同标的持仓数 < 上限 | `trade.open.max_positions_per_asset` | 3 |
| 1 | 该标的现有持仓距爆仓距离 ≥ 警戒线 | `margin.warning_pct` | 15% |
| 2 | `open_amount_usdt` ≥ 现货最小名义价值 | `trade.open.amount_usdt` | 10 USDT |
| 3 | 24h 资金费率(bps) ≥ 下限 | `trade.open.min_funding_rate_bps` | 0 bps |
| 4 | 开仓盘口覆盖率 ≤ 阈值 | `trade.open.orderbook_coverage_threshold` | 0.6 |
| 5 | 开仓基差 ≥ p20（无该标的则用全局回退） | `mi_vwap_basis_threshold.open_basis_p20` 或 `trade.open.vwap_basis_threshold_bps` | -/20 bps |
| 6 | **盈利性守卫**：开仓基差 > 平仓基差阈值 + 全部手续费 | `trade.vwap.close_threshold_percentile` | `close_basis_p20` |
| 7 | 期货 24h 成交量 ≥ 阈值 | `trade.filter.min_future_volume_24h_usdt` | 50000 |
| 8 | 现货 24h 成交量 ≥ 阈值 | `trade.filter.min_spot_volume_24h_usdt` | 100000 |

**盈利性守卫公式**：`open_vwap_basis_bps > close_threshold_bps + fee_full_bps`

### 1.3 峰值回落 + sustain 开仓确认

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.peak_pullback.pullback_pct` | 0.05 | 从峰值回落 5% 触发开仓 |
| `trade.peak_pullback.sustain_sec` | 3 | 峰值监控最低持续秒数（与 update_count 闸共同过滤脉冲/呆滞） |
| `trade.peak_pullback.monitor_timeout_sec` | 30 | 监控超时（基差长期不回落 → 放弃本轮+进入冷却，不开劣质单） |
| `trade.peak_pullback.timeout_cooldown_sec` | 120 | 监控超时后冷却（重新进入监控前的等待） |
| `trade.orderbook_health.min_update_count` | 5 | 回落确认窗口内 WS 增量次数下限（呆滞拦截） |

状态机（`_pass_peak_check`）：
```
基差首次 ≥ p20 → 实时校验24h费率(API) → 创建信号 + 记录峰值/起点update_count
基差更高        → 更新峰值
elapsed ≥ monitor_timeout_sec → 放弃本轮(信号 'monitor_timeout') + 进入 timeout_cooldown 冷却
基差 ≤ 峰值×(1-pullback_pct) 且 elapsed ≥ sustain_sec 且 update_count增量达标
              → 触发开仓（pullback）
回落但sustain/update_count不足 → 仅拦截本轮，状态保留到下轮重判
基差跌回 p20 下 / 数据中断   → 清除状态
```

> **设计原则**：回落 + sustain + update_count 三重叠加。只接受从峰值明确回落且盘口仍在活跃更新的开仓，拒绝“杯口顶部抢进”与“快照重建后冻住”场景。

### 1.4 最终风控旁路（_pre_execution_gate）

确认信号后、下单前的最后一道闸。**单标的最短链路**重读盘口、重算指标。

```
① 单标的盘口读取：gate_manager.get_orderbook(contract) + spot_manager.get_orderbook(symbol)
② 盘口新鲜度：update_time 距现在 ≤ max_orderbook_stale_sec
③ update_count 闸：复用 _peak_state 起点，校验窗口增量(gate & spot) ≥ N
④ 合并 + VWAP 基差重算
⑤ 基差 ≥ p20？盈利性守卫通过？覆盖率达标？
   通过：用这份数据下单（数据=校验数据，零缝隙）
   失败：信号标记 gate_rejected，清状态
   异常：退化为放行（不阻塞热路径）
```

| 配置项 | 默认值 |
|--------|--------|
| `trade.open.max_orderbook_stale_sec` | 5 (秒) |
| `trade.orderbook_health.min_update_count` | 5 |

### 1.5 三类冷却

| 触发场景 | 配置项 | 默认值 |
|---------|--------|--------|
| 同标的开仓后 | `trade.open.cooldown_sec` | 60 s |
| 峰值监控超时（放弃本轮，不开仓） | `trade.peak_pullback.timeout_cooldown_sec` | 120 s |
| 被交易所拒单后 | `trade.open.reject_cooldown_sec` | 300 s |

## 2. 平仓流程

入口：[`ClosingExecutor.check_and_close()`](file:///Users/jeffrey/Documents/MyProject/Arbitrage-Mi/src/calc/closing_executor.py)
触发频率：`trade.close.check_interval_sec = 0.2s`

### 2.1 平仓优先级（命中即触发）

| 优先级 | 触发条件 | 配置 | 是否走旁路 |
|-------|---------|------|----------|
| 0（最高） | **保证金爆仓风控**：距爆仓距离 < `margin.close_threshold_pct`(5%) | `margin.close_threshold_pct` | 否（紧急） |
| 1 | 资金费支付次数 ≥ 上限 | `trade.close.max_funding_payments`(30) | 否 |
| 2 | **止盈**：总盈亏(bps) ≥ p40费率(bps) × multiplier + 手续费(bps) | `trade.close.take_profit_days_multiplier`(10) | 是 |
| 3 | **累计资金费支出超阈值**（仅当当前24h费率<0时） | `trade.close.funding_cost_tolerance_ratio`(0.2) `funding_cost_min_threshold_bps`(10) | 否 |

**止盈公式**：
```
spread_profit_bps = open_spread_bps - current_spread_bps
funding_earned_bps = funding_pnl_bps    # 已收资金费 bps（含正负）
total_pnl_bps = spread_profit_bps + funding_earned_bps
threshold = (funding_rate_p40 × 10000) × take_profit_days_multiplier + fee_full_bps
触发: total_pnl_bps ≥ threshold
```

> 使用历史 `mi_gate_future_funding_rate_threshold.percentile_40` 作基准（约中位正费率），即使当前费率为负止盈仍能正常计算。

**累计资金费超阈值公式**（条件3）：
```
convergence_space = open_basis_p20 - close_basis_p20
effective_space   = max(convergence_space, funding_cost_min_threshold_bps)
threshold         = effective_space × funding_cost_tolerance_ratio
触发: abs(funding_pnl_bps) ≥ threshold  且  funding_rate_24h < 0
```

### 2.2 谷底反弹确认（仅止盈使用）

| 配置项 | 默认值 |
|--------|--------|
| `trade.valley_rebound.rebound_pct` | 0.10 |
| `trade.valley_rebound.monitor_timeout_sec` | 60 |

状态机：
```
止盈首次满足 → 记录 valley_bps + start_time + (gate, spot) update_count 起点
基差更低     → 更新 valley
基差 ≥ valley + (open_spread_bps - valley) × rebound_pct → 反弹确认平仓
elapsed ≥ timeout → 直接平仓（保底）
止盈不再满足 → 清除状态，放弃本轮
```

### 2.3 平仓最终风控旁路（仅止盈生效）

```
① 单标的盘口读取
② 盘口新鲜度 ≤ max_orderbook_stale_sec
③ update_count 闸：依赖 _valley_state 内的起点
④ 重算平仓 VWAP 基差
⑤ 收敛仍存在：gate_basis_bps < open_spread_bps
⑥ 回弹未超过 50% 收敛空间
   通过：用这份数据下单
   失败：清谷底状态，下一轮重判
   异常：退化放行
```

| 配置项 | 默认值 |
|--------|--------|
| `trade.close.max_orderbook_stale_sec` | 5 (秒) |
| `trade.orderbook_health.min_update_count` | 5 |

> **不走旁路的场景**：`margin_close`（紧急平仓）、`funding_count`（强制平仓）、`funding_cost_exceeded`。

### 2.4 平仓失败冷却

`trade.close.cooldown_sec = 60s`，平仓失败后该标的 60s 内不重试；保证金爆仓风控不受冷却约束（每轮都检查）。

## 3. 保证金风控（逐仓）

### 3.1 公式

```
liq_price        = future_open_price × (1 + 1/leverage - maintenance_rate)   # 空头
liq_distance_pct = (liq_price - current_future_price) / current_future_price × 100
```

| 参数 | 来源 | 默认值 |
|------|------|--------|
| `leverage` | `margin.leverage` | 2 |
| `maintenance_rate` | `mi_gate_future_contracts.maintenance_rate`，缺失则 `margin.default_maintenance_rate` | 0.005 |

### 3.2 三层防御

| 层级 | 阶段 | 阈值 | 行为 |
|------|------|------|------|
| 预防 | 开仓 | `margin.warning_pct` (15%) | 该标的距爆仓距离 < 阈值 → 拒新仓 |
| 监控 | 持仓 | — | 5s 计算并推送前端 |
| 应急 | 平仓 | `margin.close_threshold_pct` (5%) | 触发紧急平仓，最高优先级 |

### 3.3 风险隔离

- 单仓爆仓不影响其他仓位（逐仓独立保证金）
- 现货资产物理隔离于另一交易所（Binance）
- 系统在距爆仓 5% 时主动平仓，避免真实爆仓
- 即使主动平仓失败，单仓最大损失 = `open_amount_usdt / leverage`

## 4. 盘口健康度门禁（更新次数闸）

**目的**：拦截"WS 增量失败 → 盘口冻住 → 快照重建后立即命中 sustain"的呆滞场景（如 MBOX 类）。

### 4.1 工作机制

- OrderBook 内部维护 `update_count`：每帧 WS 更新 +1（Gate 期货快照重建后清零；Binance 现货无快照重建场景）
- sustain / peak / valley 进入监控时记录 `(gate_uc_start, spot_uc_start)`
- 旁路风控比对：`update_count_now - update_count_start ≥ min_update_count`（gate 与 spot 各自达标）
- 不达标 → 判定盘口呆滞 → 拒开 / 拒平

### 4.2 配置

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `trade.orderbook_health.min_update_count` | 5 | sustain 窗口内 WS 更新次数下限（开仓平仓共用） |

设为 ≤ 0 时全链路放行（应急关闭开关）。

### 4.3 嵌入位置

| 位置 | 类 | 起点状态 |
|------|----|---------|
| 峰值回落确认内部校验 | `TradingExecutor._pass_peak_check` | `_peak_state` |
| 开仓最终风控旁路 | `TradingExecutor._pre_execution_gate` | `_peak_state` |
| 平仓最终风控旁路 | `ClosingExecutor._pre_execution_gate` | `_valley_state` |

## 5. 数据流

```
WebSocket（Binance @depth5@100ms + Gate update WS+REST快照）
    ↓
本地 OrderBook（含 update_count）
    ↓
合并 → 计算对冲指标(VWAP / coverage)
    ↓
┌─ 实时 PnL（5s）─────────────────┐
│ 浮动盈亏 + 资金费 + 爆仓价 + 距爆仓
│ → 推送前端 + 更新 _holding_liq_distance
└──────────────────────────────────┘
    ↓
┌─ 开仓循环（0.2s）──────────────┐
│ 风控 → 冷却 → 峰值回落+sustain → 旁路 │
│ → 调用成交引擎下单                  │
└─────────────────────────────────┘
    ↓
┌─ 平仓循环（0.2s）──────────────┐
│ P0 爆仓风控 → P1 资金费次数    │
│ → P2 止盈+谷底+旁路            │
│ → P3 累计资金费                │
│ → 调用成交引擎平仓            │
└──────────────────────────────────┘
```

热路径约束：开仓/平仓循环（0.2s）仅做内存读取 + 纯计算 + ExecutorClient 下单；REST 调用（实时费率校验）仅在峰值首次入场时执行一次。

## 8. VWAP 计算说明

- VWAP（Volume Weighted Average Price）是市价单按盘口逐档成交的真实加权均价
- **VWAP 不需要满足交易所 tick_size**（那是限价单约束）
- 基差计算保留 VWAP 真实精度，不做 floor 截断
- 实际成交后用 `exec_price` 重算基差并写入 DB，统一为实际成交口径
